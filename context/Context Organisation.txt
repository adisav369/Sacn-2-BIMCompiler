# Context Organisation — Claude's POV

## How Context Actually Works in This Project

Claude Code auto-loads two files every session:
1. **CLAUDE.md** — prime rule, standing rules, session protocol
2. **MEMORY.md** — doc map, stable facts, user preferences, topic file index

These two files ARE the context map. They already solve the "brilliant but
forgetful senior engineer" problem. No paste templates needed — Claude Code
reads them automatically.

**What's working well:**
- CLAUDE.md + MEMORY.md = orientation in <5 seconds
- PROGRESS.md = current state, gates, what's next
- Doc map in MEMORY.md = load-on-demand pointers to 11 docs
- Topic files (memory/*.md) = deep dives on architecture, traps, conventions
- Auto-compression = context never runs out mid-session

**What's NOT needed:**
- Splitting into repos — Maven modules already isolate (DAGCompiler doesn't
  import ORMSandbox). Monorepo = one git push, one CI. Zero benefit to split.
- Paste-in prompt templates — Claude Code loads CLAUDE.md/MEMORY.md natively
- CONTEXT_dag_pipeline.md / CONTEXT_bom_verbs.md — these duplicate existing
  docs (BOMBasedCompilation.md, BIM_COBOL.md) which the doc map already points to

### Gap 3: No Sacred Files List

When I edit a file, I don't know if it's fragile or safe to touch. A short
guard list prevents accidents on files where a wrong edit breaks everything.

**Action: Add to CLAUDE.md** (not a separate file — it must auto-load):

```
## Sacred Files (edit with extreme care)
- migration/*.sql — append only, never modify existing migrations
- BuildingCompiler.java — main orchestration, 500+ lines, many dependencies
- RosettaStoneGateTest.java — defines G1-G6 gates, changes break CI
- X_M_BOM.java / X_M_BOMLine.java — EntityType guards, GodMode bypass
```

### Gap 4: Verb Count in 4 Test Files

Adding a verb requires updating registry count assertions in 4 separate files:
- VerbRegistryTest.java

- ConvenienceVerbTest.java

This is a code smell, not a context problem. Fix: single constant
`VerbRegistry.EXPECTED_COUNT = 41` or remove redundant count assertions.

## The Real Strategy

The original DeepSeek analysis was written for generic Claude (API/chat).
Claude Code is different — it has:

- **Auto-loaded project files** (CLAUDE.md, MEMORY.md)
- **Persistent memory** across sessions (memory/*.md topic files)
- **Tool access** to read any file on demand (Glob, Grep, Read)
- **Auto-compression** when context gets long
- **Subagents** for parallel exploration without consuming main context

The context organisation strategy for Claude Code is therefore simpler:

1. **CLAUDE.md** = rules + sacred files (auto-loaded, <30 lines)
2. **MEMORY.md** = map + facts + preferences (auto-loaded, <200 lines)
3. **PROGRESS.md** = current state (read at session start)
4. **context/SCHEMA_QUICKREF.md** = compact DB reference (load on demand)
5. **Existing docs** = deep dives (load via doc map when needed)

That's it. Five files. No templates, no phases, no repo splits.
