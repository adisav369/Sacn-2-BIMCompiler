TODO-1  BOM product_type — Room-to-Set matching column
------------------------------------------------------
Problem:
  v_qualified_bom currently has no way to match a room type (bedroom,
  living, kitchen) to eligible BOM sets. It only knows bom_type tier
  (ROOM/SET/ITEM) and min_space_mm. A bedroom would get any SET that fits
  by size, which could produce a sofa set in a bedroom.

Required:
  Add a product_type column to m_bom (e.g. 'BEDROOM', 'LIVING', 'KITCHEN',
  'BATHROOM', 'UNIVERSAL'). The cascade query adds:
    WHERE bom.product_type = ? OR bom.product_type = 'UNIVERSAL'
  Room type from v_verified_room_boundary drives the bind parameter.

Priority within type:
  fit_priority on m_bom_line already exists but was seeded only at DEFAULT.
  The user's proposal: fit_priority lives on the BOM product itself (m_bom),
  not the child line. A sofa set has higher priority than dining set for a
  living room because the architect declared it so, not because of size.
  Current fit_priority on m_bom_line seeds are for size-gating, not type
  preference. These are two different things — both needed, currently conflated.

Impact:
  - New column: m_bom.product_type TEXT (CHECK constraint, known values)
  - Update v_qualified_bom: add product_type to SELECT + caller bind param
  - Update v_verified_room_boundary or caller to expose room_type as bind key
  - Migration: seed product_type for all 35 current m_bom rows
  - PREFAB_ARCHITECTURE.md §3.1 and VIEW_CONTRACTS.md §5.1 to be updated
  - Name 'product_type' is placeholder — architect to confirm final name

Deferred until: Phase 4 watchdog session. Do not implement before v_qualified_bom
join (product_ref FK) is resolved and verified.

TODO-2  Phantom Spatial Children — BOM MANIFEST enforcement
-----------------------------------------------------------
Problem:
  A toilet bowl placed by the compiler has no declared relationship to the
  door it faces or the wall it backs against. Rotation is currently resolved
  by c_orderline.orientation + FixturePlacer heuristics — fragile,
  coder-pressure-sensitive, and wrong in non-standard layouts (e.g. WC
  outside a gas station where the door is the exterior station wall, not
  a dedicated toilet room door).

Required:
  Every fixture-level BOM (TOILET_BLOCK_FIXTURES, BATHROOM_WC_SET etc.)
  must carry phantom spatial children in m_bom_line:
    role = 'WALL_BACK'   — the wall the fixture backs against
    role = 'FACE_TOWARD' — the element (door, opening) the fixture faces
    role = 'CLEARANCE_FRONT' — minimum clear space in front
  These are not physical elements. They are spatial contracts that lock the
  block's orientation before any child item is placed.

  rotation_rule = 'FACE_AWAY_FROM_WALL' resolves correctly ONLY when
  WALL_BACK is declared by the phantom child, not inferred at runtime.
  Without this, the compiler guesses — and guesses wrong under edge cases.

Impact:
  - m_bom_line: allow role values WALL_BACK, FACE_TOWARD, CLEARANCE_FRONT
    with child_name_pattern = NULL (phantom = no physical geometry)
  - ad_assembly_manifest table (already designed in PREFAB_ARCHITECTURE.md)
    to be seeded with face contracts for all fixture BOMs
  - FixturePlacer: rotation resolution reads WALL_BACK phantom, not heuristic
  - PREFAB_ARCHITECTURE.md §"Self-Orienting BOMs" already describes this
    conceptually — the phantom children are the implementation of that concept
  - Applies to: TOILET_BLOCK_FIXTURES, DUPLEX_BATHROOM_SET, BATHROOM_WC_SET,
    KITCHEN_CABINET_SET (WALL_BACK = counter wall), BED_SET (WALL_BACK = headboard)

Priority: HIGH — prevents rotation bugs recurring under coder pressure.

TODO-3  All Physical Elements Must Come From Component/Mesh Library
-------------------------------------------------------------------
Rule (non-negotiable):
  Every physical element in compiled output must trace to one of:
  (a) component_definitions — extracted LOD geometry from reference IFC
  (b) ad_parametric_mesh — registered grammar in Mesh2Library contract
  No element may be invented inline in Java. No geometry may be hardcoded.

Known violations to investigate (audit in progress):
  - TB-LKTN walls reported as ultra-thin — suggest invented geometry,
    not sourced from component library
  - TB-LKTN doors and some furniture items suspect
  - New roof (porch) and exterior drain perimeter mesh — check whether
    registered in ad_parametric_mesh AND documented in Mesh2Library.txt
    with grammar definition. Registration in one place without the other
    is a half-measure and will cause drift.

Required if new mesh type is needed:
  1. Define grammar in Mesh2Library.txt (shape parameters, vertex contract)
  2. INSERT into ad_parametric_mesh (mesh_type, generator_class)
  3. INSERT into ad_parametric_mesh_param (all shape parameters)
  4. Java class implements sealed ParametricMesh interface
  5. ad_product_dim entry for the resulting bounding dims
  All five steps required. Missing any one = violation.

TODO-5  Test Integrity — No Bypass, No Gutting
----------------------------------------------
Rule (non-negotiable):
  Tests prove claims. A passing test that does not test is a lie.
  Removing a throw statement to make a test pass is fraud.
  Modifying data to flat positions to bypass the pipeline is regression.

Prohibited patterns:
  @Disabled, @Ignore, assumeTrue(false) on non-trivial tests
  Empty catch blocks swallowing exceptions
  Commented-out throw new MetadataMissingException(...)
  Direct coordinate literals in placement resolvers
  UPDATE c_orderline SET position_value = <literal> to fix a test

If any of the above are found in audit:
  The test must be restored. The underlying cause must be fixed.
  A failing test is always preferable to a silenced one.
  Watchdog will reject any commit that silences a test without fixing root cause.

TODO-6  BOM Cascade — Set Atomicity Enforcement
-----------------------------------------------
Rule:
  Once a BOM set is selected and placed, its internal child positions
  (m_attribute dx/dy/dz, rotation_rule) are not renegotiated.
  The set is placed as a rigid block. Individual items within it are
  not re-sorted, re-rotated, or re-positioned at runtime.

Current risk:
  FurnitureBOMResolver.expandBOMNode() computes child world positions
  from anchor + offset. If the anchor itself is wrong (calibration debt)
  the whole set shifts but stays internally consistent.
  Risk is not in the set logic — risk is callers passing a wrong anchor.
  v_verified_room_boundary is the gate that prevents wrong anchors
  from reaching the resolver. Once Phase 4 is live this is enforced.

Document for Phase 4:
  ArchUnit gate should verify FurnitureBOMResolver only reads room
  anchor from v_verified_room_boundary result — never from a raw
  ad_room_boundary query or a hardcoded default.

TODO-7  Phantom Spatial Children — Full Implementation (expands TODO-2)
-----------------------------------------------------------------------
Scope (architect's intent):
  Phantom orientation contracts must cover ALL cases, not just toilets:
  - Room facing front door (which wall is ENTRY for any room)
  - Furniture set anchor wall (which wall is WALL_BACK for BED_SET, SOFA_SET)
  - Chair facing table (FACE_TOWARD within a SET, not just room-level)
  - Kitchen counter facing work aisle (WALL_BACK = counter wall, FACE=open)
  - Gas station WC: door is exterior (ENTRY face = EXTERIOR, not WALL)

Data model:
  m_bom_line phantom rows — same table, flag is_phantom=1 (new column):
    role = 'ENTRY'        child = door element ref  (which side is the entrance)
    role = 'WALL_BACK'    child = wall ref           (which wall to anchor against)
    role = 'FACE_TOWARD'  child = sibling child ref  (chair faces this element)
    role = 'CLEARANCE'    child = NULL               (open space, no physical element)
  Phantom children have child_name_pattern = NULL and no geometry.
  They participate in rotation resolution only, never in geometry emission.

Java implementation — interface pattern (minimal, readable):
  Introduce PhantomContract interface:
    interface PhantomContract {
        Face anchorFace();          // which room face this BOM backs against
        Optional<String> facesRef();// sibling child ref this element faces
    }
  BomChildRecord implements PhantomContract when is_phantom=1.
  RotationResolver (new class) loops:
    for each child in BOM:
        if child.isPhantom() -> register face contract
        else -> resolve rotation from registered contracts
  This replaces FixturePlacer heuristics. One loop, no conditionals per fixture.

Debug logs required:
  [PHANTOM] <assembly_id> ENTRY=<wall_direction> WALL_BACK=<wall_ref>
  [ROTATE]  <child_ref> rotation_rule=<rule> resolved=<angle_rad>
           reason: WALL_BACK at <direction> → FACE_AWAY = <opposite_direction>
  [ROTATE-WARN] <child_ref> rotation_rule=FACE_AWAY_FROM_WALL but no WALL_BACK
               phantom declared — falling back to orientation column value <n>
  Coder reads the WARN line and knows exactly which BOM is missing its phantom.

Cascade elegance:
  Room-level: room has ENTRY face (front door wall) — declared once in
    ad_room_slot or ad_assembly_manifest.
  Set-level: BED_SET WALL_BACK inherits from room ENTRY + UBBL rule
    (bed against wall opposite door, or longest uninterrupted wall).
  Child-level: chair FACE_TOWARD = dining table sibling ref.
  Each level declares only what it knows. Compiler accumulates downward.

TODO-8  Wall Prefabs by Dimension — Structural Catalog
------------------------------------------------------
Background:
  SH and DX walls have high-quality LOD meshes in component_definitions.
  These must be kept and used. Structural elements are not invented inline —
  they are placed via c_orderline with BOUNDARY rule + extracted coords.
  The compiler manages these correctly for SH/DX.

TB-LKTN gap:
  TB-LKTN IfcPlate elements (20 curtain panels) have family_ref=NULL —
  no component_definitions entry, no ad_product_dim backing.
  These are untraced structural elements outside the catalog contract.

Required — wall prefab catalog approach (like contractor cut-to-length):
  1. Extract wall mesh types from SH/DX component_definitions by LOD geometry
     (e.g., Basic Wall:Wall-Ext_102Bwk-75Ins-100LBlk-12P → 289mm total thickness)
  2. Register each unique wall type in component_definitions with:
       name = wall type string (family:type from Revit)
       product_type = 'WALL_EXT' / 'WALL_INT' / 'WALL_PARTY'
       width_mm = thickness (e.g., 289mm exterior, 94mm partition)
  3. ad_product_dim entry for each: width=thickness, depth=variable (cut to length),
     height=storey clear height
  4. TB-LKTN c_orderline: set family_ref to matching wall type from catalog
     Compiler selects closest thickness match from catalog for each panel.
  This mirrors how a contractor orders "289mm brick-block wall, cut to 3600mm".
  Variable dimension (length) is derived from room boundary, not stored in catalog.

TODO-9  Component Dimensional Fit — ±10% Tolerance with Scale Transform
-----------------------------------------------------------------------
Problem:
  TB-LKTN front door should be double-leaf. DX has a double-leaf door in
  component_definitions. Coder rejects it as "too wide". This rejection
  is wrong — a scale transform of ±10% on the constrained dimension (width)
  is architecturally acceptable and reflects real contractor practice
  (cut door frame to opening width within tolerance).

Proposed compiler behavior:
  When selecting a component from component_definitions by name pattern:
    1. Find exact match by dimensions → use as-is (current behavior)
    2. If no exact match: find nearest match within ±10% on width AND height
    3. Apply scale transform:
         scale_x = target_width  / source.width
         scale_y = target_height / source.height  (only if height also differs)
       cap: neither scale_x nor scale_y may exceed 1.10 or fall below 0.90
    4. Write with scale applied to geometry vertices at compile time
    5. Provenance note in element_instances: scaled_from=<source_name>,
       scale_x=0.9, scale_y=1.0 (for traceability)

Door-specific example:
  TB-LKTN front door opening: target_width=1600mm (double leaf)
  DX double-leaf door: source_width=1800mm
  scale_x = 1600/1800 = 0.889 → within 10% tolerance → APPLY
  Result: DX door geometry scaled to 1600mm, used for TB-LKTN front entry.

Scope:
  Applies to doors, windows, and structural panels (not furniture — furniture
  sets are atomic, see TODO-6). Components where a nearest catalog fit
  within tolerance is architecturally correct.

Implementation note:
  transformAndWriteGeometryScaled() already exists in MEPWriter for fixtures.
  Research whether this method can be generalised to any component write path.
  If yes, the tolerance-fit logic is a selector wrapper, not a new writer.

Debug log required:
  [SCALE-FIT] <element_ref> source=<name> target_w=<n>mm source_w=<n>mm
              scale_x=<f> (within 10% tolerance — applying)
  [SCALE-REJECT] <element_ref> nearest=<name> delta=<n>% (exceeds 10% — skip)
