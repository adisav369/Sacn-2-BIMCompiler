IFCtoBOM Gap Analysis — S140 Database Review
=============================================
Date: 2026-04-04
Scope: What IFCtoBOM writes to *_BOM.db and what IFCtoERP writes to ERP.db
Test stones: SH (58 el), DX (1119 el), RM (6786 el)

EXTRACTION IS DONE. extractIFCtoDB.py → *_extracted.db is correct and complete.
This analysis is about the NEXT stage: IFCtoBOM + IFCtoERP.


1. DATA FLOW (current)
======================

  IFC file
    → extractIFCtoDB.py → XX_extracted.db (elements, spatial, aggregates, materials)
    → IFCtoBOMPipeline.java → XX_BOM.db (BOMs, BOM lines, products)
    → IFCtoERP.java → ERP.db (MEP recipes, joint pieces, products)
    → DAGCompiler → output.db (C_OrderLine, compiled placement)

  XX_BOM.db holds: WHAT (products) + WHERE (tack offsets per BOM line)
  ERP.db holds: HOW (MEP recipes, discipline rules, validation)

  Discipline lives ONLY in ERP.db (AD_Org table, AD_Org_ID on M_BOM_Line).
  BOM.db has AD_Org_ID=0 on all lines — discipline-blind by design.

3. SPEC GAPS FOUND
==================

GAP-A: child_product_id in BOM.db is IFC-source-specific, not abstract
-----------------------------------------------------------------------
  BBC.md principle: products come from component_library.db catalog.
  Reality: child_product_id = "M_Supply Diffuser - Sidewall:450 x 200" (Revit family name)
  This is not reusable across buildings from different authoring tools.
  An ArchiCAD project would have completely different names for the same physical product.

  The component_library.db DOES have abstract products but the BOM.db doesn't reference them.
  IFCtoBOM writes the raw IFC element name as the product ID.

GAP-B: MEP_RECIPE bom_ids are building-stamped
-----------------------------------------------
  Every MEP recipe in ERP.db has prefix "RM_", "DX_", "CE_", etc.
  "RM_ACMV_L1_RUN_1" is specific to Revit_MEP building.
  Same duct run pattern recurring in another building gets a new recipe.
  No pattern reuse across the fleet — each building reinvents its recipes.

  The DATA FLYWHEEL (BBC §9) cannot learn from this because recipes are named per-building.
  Abstract alternative: "ACMV_DUCT_RUN_TYPE_A" defined once, instantiated per-building via Order.

GAP-C: M_Product in ERP.db is building-tagged, not catalog
-----------------------------------------------------------
  M_Product.building_type = 'Revit_MEP' ties products to one source.
  "M_Duplex Receptacle:Standard" in Revit_MEP is the same physical product as
  "Duplex Receptacle" in any other IFC source — but they get separate M_Product rows.

GAP-D: No IfcRelAggregates consumption in RM
---------------------------------------------
  RM has 0 ASSEMBLY BOMs. SH has 2 (curtain wall), DX has 2 (stairs).
  RM's rel_aggregates table IS populated during extraction but StructuralBomBuilder
  requires matched children in the spatial structure. RM is IFC2x3 with different
  aggregate patterns — the assembly code may not be finding them.
  Potential: RM curtain walls, railing assemblies could collapse into sub-BOMs.

GAP-E: Discipline in BOM.db is AD_Org_ID=0 (undifferentiated)
--------------------------------------------------------------
  All 278 RM_BOM.db lines have AD_Org_ID=0.
  Discipline separation (S103) puts MEP COUNTS into ad_sysconfig and YAML,
  but the BOM lines themselves don't carry discipline.
  A supply diffuser (ACMV) and a duplex receptacle (ELEC) sit side by side
  in the same FLOOR BOM with no distinction.
  ERP.db MEP_RECIPE BOMs carry discipline via the prefix (RM_ACMV_, RM_CW_).

GAP-F: ERP.db MEP_RECIPE component_type still says "MAKE"
----------------------------------------------------------
  IFCtoERP.java INSERT was fixed to remove 'LEAF' literal, but existing rows
  in ERP.db still have component_type='MAKE' (was 'LEAF' before S140).
  Column is deprecated but ERP.db hasn't been re-generated yet.
  Non-issue for compilation (column ignored) but stale data.

NOT-A-GAP: CLUSTER verb_ref carries world coordinates
------------------------------------------------------
  This is BY DESIGN. BBC §4 Tack Convention: BOM lines carry offsets relative
  to parent LBD. For CLUSTER, each instance offset IS the tack position.
  Reuse comes from the verb PATTERN (TILE/ROUTE/FRAME), not from CLUSTER.
  CLUSTER is the honest "I found no pattern" fallback.

NOT-A-GAP: BOM.db has no MEP separation
----------------------------------------
  This is BY DESIGN per S103 Discipline Separation. BOM.db is the WHAT.
  Discipline (the HOW) lives in ERP.db. DisciplineBomBuilder writes counts
  to ad_sysconfig; the actual MEP routing recipes go to ERP.db via IFCtoERP.
  The BOM.db FLOOR BOMs carry ALL elements (ARC+STR+MEP) for spatial integrity.


4. ROOT CAUSE
=============

IFCtoBOM writes child_product_id = element's IFC name verbatim.
It does NOT look up or create an abstract product in component_library.db.
The "product catalog" mapping step is missing from the pipeline.

IFCtoERP writes abstract shim names (DUCT_STRAIGHT_325MM) for MEP recipes,
which IS correct — but stamps them with building prefix (RM_ACMV_L1_RUN_1).

The spec (BBC.md) assumes products are abstract catalog entries.
The code assumes products are IFC element names.
This divergence is the source of non-reusability.


5. PLANNED SESSIONS (candidates — not yet decided)
===================================================

#A — Product Catalog Mapping in IFCtoBOM
  Problem: child_product_id = raw IFC name, not catalog product
  Approach: After extraction, map IFC family:type → M_Product in component_library.db
  using ad_element_mep_alias cascade (already exists for MEP) extended to ARC/STR.
  Where no catalog match: create abstract stub with dimensions from AABB.
  Test: SH, DX, RM — verify child_product_ids resolve to library products.

#B — Abstract MEP Recipe Patterns
  Problem: RM_ACMV_L1_RUN_1 is building-specific, not reusable
  Approach: IFCtoERP writes pattern-type recipes (ACMV_DUCT_RUN_TYPE_A) based on
  topology signature (elbow-straight-fitting sequence + dimension band).
  Building instantiation via C_OrderLine, not recipe duplication.
  Depends on: #A (products must be abstract first)
  Test: RM — verify recipe count drops from 783 to ~20-50 pattern types.

#C — RM Assembly BOMs from IfcRelAggregates
  Problem: RM has 0 ASSEMBLY BOMs despite populated rel_aggregates
  Approach: Debug StructuralBomBuilder for IFC2x3 aggregate handling.
  May need to relax the "matched children in spatial structure" requirement.
  Test: RM — verify curtain wall/railing assemblies become sub-BOMs.

#D — AD_Org_ID Discipline Tagging in BOM.db
  Problem: All BOM lines have AD_Org_ID=0
  Approach: DisciplineBomBuilder already knows disciplines — write AD_Org_ID
  on m_bom_line when the element's discipline is known from extraction metadata.
  This is informational (walker doesn't branch on it) but enables reporting.
  Test: RM — verify MEP lines carry correct AD_Org_ID (3-8 per discipline).

#E — M_Product Deduplication Across Buildings
  Problem: Same physical product gets separate M_Product rows per building
  Approach: M_Product lookup by (dimensions + IFC class) before INSERT.
  If match found within tolerance band, reuse existing product_id.
  Depends on: #A (abstract naming first)
  Test: SH+DX — verify shared products (walls, doors) share product_ids.
