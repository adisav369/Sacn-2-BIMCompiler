§1  PIPELINE ALGORITHM — DATA MOVEMENT CHAIN
═══════════════════════════════════════════════════════════════

Stage 1 — IFC Extraction (black-box input)
  placement_extractor.py
    extract_placements()      reads IFC parser output → groups by (ifc_class, storey)
                              assigns ordinals by position sort → writes I_Element_Extraction
                              uses _f32() rounding throughout (float32 precision)
    _f32()                    rounds float64 → float32 to match R*Tree storage precision
    classify_orientation()    EW/NS/POINT from bounding box aspect ratio (wall-like only)
    generate_insert_sql()     emits INSERT OR IGNORE statements (idempotent)

  IFCtoERP.java
    classifyElement()         11 MEP IFC classes → 31 piece types → ERP.db
    buildAnchorTable()        IfcSlab → storey floor Z values → ad_mep_anchor
    extractArchetypes()       coverage topology: group by (disc, ifcClass, dz_band)
                              routing topology: one recipe per (storey + disc + run)

Stage 2 — BOM Tree Walk (the spatial reconstruction)
  PlacementCollectorVisitor
    onSubAssembly()           push worldAnchor = parent_anchor + line.dx/dy/dz + bom.origin_x/y/z
    onSubAssemblyComplete()   pop anchorStack, rotationStack, storeyStack, disciplineStack
    onLeaf()                  THE CRITICAL PATH:
                                anchor     = anchorStack.peek()
                                offsets[]  = expandVerb(verbRef, qty, leafDx, leafDy, leafDz)
                                iHalfW/D/H = allocated_*_mm / 2  (or M_Product intrinsic)
                                cx = anchor[0] + offsets[qi][0] + iHalfW   ← centroid formula
                                cy = anchor[1] + offsets[qi][1] + iHalfD
                                cz = anchor[2] + offsets[qi][2] + iHalfH
                                → new Placement(minX=cx-iHalfW, maxX=cx+iHalfW, ...)
    onPhantom()               consumes tack coordinate, emits NO placement record
    expandVerb()              TILE / ROUTE / FRAME / CLUSTER / SPRAY / null(=PLACE)
                              unknown prefix → BIMLogger.warn + origin fallback
    emitGeoSummary()          all-pairs relative offset delta: compiled vs extracted by GUID
                              pairDrift = max(|Δcx_ij_compiled - Δcx_ij_extracted|) × 1000mm

Stage 3 — Write to output.db
  ElementPersistence
    writeElementMeta()        INSERT elements_meta + elements_rtree
    positionKey()             1mm-rounded (cx, dims) → dedup key
    P05/P06 jitter guard      duplicate position → +2mm Z offset; prints to System.err
    writeGeometry()           library LOD mesh → base_geometries (SHA-256 of 1mm-rounded verts)

§2  GEO DEBUG STATEMENTS — WHITE-BOX COVERAGE
═══════════════════════════════════════════════════════════════

GEO is a white-box instrument. Its role is to expose the internal formula execution
so a developer can step through the math without a debugger. It is NOT the correctness
gate — see §3 for that.

32 statements total across PlacementCollectorVisitor + ShimMatcher + CompilationPipeline.

TACK channel (per-element proof):
  ENTER  PCV:240   anchor accumulation at each BOM depth
  ROT    PCV:321   rotation applied to leaf offset (local→world)
  LEAF   PCV:459   full formula: anchor + offset + half → centroid, with GUID
  CHAIN  PCV:467   ancestor path BUILDING→FLOOR→ROOM→LEAF
  DIMS   PCV:470   W×D×H in mm — proves no truncation or dimension swap
  CONTAIN PCV:758/761  leaf within parent AABB → LMP detection
  EXIT   PCV:266   stack correctly unwound

WORKSHOP channel (UOM recompute):
  ENTER / RECOMPUTE / TACK_IO / REJECT   PCV:377-391

SHIM channel (MEP host resolution):
  SHIM_ENTER / SHIM_MATCH / SHIM_MISS    ShimMatcher:113-163

SUMMARY (post-walk verification):
  PCV:993/1010   DRIFT count + worst-case mm across all-pairs relative offsets

GEO gaps (all minor):
  1. Unknown verb prefix (PCV:557) — logs WARN at COMPILE level, not in GEO LEAF path.
     A new unrecognized verb would place all instances at origin; LEAF GEO shows
     origin centroid with no verb attribution. Risk: MEDIUM but rare.
  2. Rotation rule parse error (PCV:859) — NumberFormatException → silent 0.0 fallback.
     No log at any level. LEAF ROT would show "ROT 0.0000rad" which looks intentional.
     Risk: LOW (edge case, caught by unexpected element orientation in output).
  3. Product missing / no allocated dims (PCV:345) — element skipped, WARN only.
     No GEO LEAF emitted. Caught by element count gate G1. Risk: LOW.

GEO world-origin limitation:
  SUMMARY's pairDrift metric cancels world origin by design (relative offset deltas).
  Zero DRIFT in SUMMARY does NOT prove absolute building position is correct — only
  that elements are correctly placed relative to each other. Absolute position proof
  requires the ENTER log line at depth=0 to be read manually against the survey origin.
  This is acceptable because absolute position is verified by the black-box gate (§3).

═══════════════════════════════════════════════════════════════
§3  POST-PROCESS BLACK-BOX FIDELITY GATE — THE REAL CORRECTNESS PROOF
═══════════════════════════════════════════════════════════════

ExtractedGeometryTruthTest.java — three-tier black-box gate

  T1 — Element Count (class-agnostic)
    Query: COUNT(*) FROM elements_meta JOIN elements_rtree
    Both extracted.db and output.db must return identical totals.
    Catches: dropped elements, phantom duplicates.

  T2 — Volume Conservation
    Query: SUM(round(dx*1000) * round(dy*1000) * round(dz*1000))
    Total AABB volume in mm³ must match within 0.1%.
    Catches: dimension swaps, truncation, wrong allocated dims.

  T3 — Placement Match (definitive)
    Every bbox in extracted.db is represented as a multiset key:
      "minX_mm|maxX_mm|minY_mm|maxY_mm|minZ_mm|maxZ_mm"
    T3 computes the symmetric difference of these multisets.
    PASS condition: missing=0 AND phantom=0.
    Tolerance: 1mm (integer round of float×1000).
    Catches: wrong position, wrong size, wrong world origin, missing elements,
             extra elements, any coordinate drift > 1mm.

  This test is standalone: no BuildingRegistry, no SpatialDigest, no PlacementProver.
  It takes two SQLite files and produces truth.

TotalityContractTest.java — per-element AABB diff using SpatialDiff engine
  Matches elements by position-sort order within each ifc_class.
  Bands: EXACT (≤1mm) / DRIFT (1–50mm) / SHIFT (>50mm) / MISSING / EXTRA.
  W-TOT-1/2/3: SH, DX, TE must have 0 DRIFT, 0 SHIFT, 0 MISSING, 0 EXTRA.

These two tests together constitute a complete input=output fidelity assertion:
  ExtractedGeometryTruthTest.T3  →  any element that existed in IFC extraction
                                     must exist in output.db at the same position ±1mm
  TotalityContractTest           →  no element may be displaced, missing, or phantom

§4  RELATIONSHIP BETWEEN GEO AND THE BLACK-BOX GATE
═══════════════════════════════════════════════════════════════

GEO (white-box):
  Purpose: developer observability during compilation.
  Evidence: formula execution visible per-element (anchor chain, verb offsets, centroid).
  Limitation: SUMMARY metric cancels world origin; cannot prove absolute placement alone.
  Role: diagnostic first-line when T3 fails — tells you WHERE in the formula the drift is.

ExtractedGeometryTruthTest T3 (black-box):
  Purpose: correctness gate — input must equal output.
  Evidence: multiset of integer-mm bboxes, symmetric difference must be empty.
  Coverage: every element, every dimension, every position, including world origin.
  Role: definitive pass/fail. If T3 passes, the pipeline is correct by definition.

CONCLUSION: GEO gap §2 (world-origin not validated by SUMMARY) is NOT a risk.
  If the world origin is wrong, every element is displaced and T3 fails with
  missing=N, phantom=N for the entire building. GEO's white-box limitation is
  closed by T3's black-box scope. The two instruments are complementary and together
  leave no unverified path in the pipeline.

The "rosy reports" concern is resolved:
  - GEO SUMMARY showing DRIFT=0 with a wrong world origin → T3 catches it (all elements phantom).
  - P05-JITTER printing to System.err not GEO channel → not a correctness issue; jitter is
    a display guard, not a position mutation. The +2mm Z shift is ≤ T3's 1mm tolerance only
    if it was already within 1mm; if the shift causes T3 mismatch, test fails.
    NOTE: 2mm > 1mm tolerance, so P05-JITTER on an otherwise-correct element WOULD fail T3.
    This means P05-JITTER events are surfaced by T3 indirectly. Track with W-P05 witness.

§5  OPEN ITEMS (not defects — items requiring watch)
═══════════════════════════════════════════════════════════════

OI-1  P05-JITTER +2mm Z shift exceeds T3's 1mm tolerance.
      If an element legitimately lands at the same position as another,
      the jitter guard moves it 2mm and T3 will flag it as phantom+missing pair.
      Current state: no P05-JITTER events in SH, DX, CP (clean buildings).
      Risk for MEP-dense buildings (TE): possible if sprinkler heads tile at identical Z.
      Action: confirm TE T3 scope includes jitter-affected elements; or raise T3 tolerance
      to 3mm for P05 classes only.

OI-2  ExtractedGeometryTruthTest.BUILDINGS array covers only SH and DX.
      TotalityContractTest.GATE_SCOPE covers RE_SH, RE_DX, CO_TE.
      35-building Rosetta Stone fleet is not fully covered by T3.
      Action: BUILDINGS array should be expanded as each building passes RosettaStoneGateTest.

OI-3  Unknown verb prefix (PCV:557) is silent in GEO.
      No witness claim exists for this fallback path.
      Action: add BIMLogger.geo("TACK", "VERB_UNKNOWN {} prefix={} — origin fallback") before
      the fallback loop, or add a W-VERB-UNKNOWN witness in the gate test.
