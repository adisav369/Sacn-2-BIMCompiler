    Standards Compliance — Regulatory Proof Engine¶

    Foundation: DocValidate (construction validation) · BIM_COBOL (verb grammar) · DocAction_SRS (lifecycle) · DATA_MODEL (ERP schema) · StrategicIndustryPositioning (moat §3)

    Standards compliance is not validation. Validation asks: is this building correct? Compliance asks: can I prove it to a regulator?

    The difference is the output. DocValidate produces PASS/FAIL. The Standards Compliance module produces a signed proof chain — a machine-verifiable document that traces every regulatory decision from room dimension to statute citation, reproducible independently by any reviewer with access to the same compiler and library hash.

    No other BIM tool produces this. Regulators currently receive geometry and reverse-engineer intent. This module inverts that: regulators receive proof, geometry is secondary.

    The Problem This Solves¶

    A building permit in Malaysia takes 6–18 months. 90% of that time is human reviewers manually checking drawings against UBBL clauses. The reviewer opens a PDF, measures a room, finds a clause, writes a comment. The architect revises. The cycle repeats. There is no machine in this loop.

    The same problem exists in every jurisdiction: UK Building Regulations, Singapore BCA, Australian NCC, UAE IBC-adopted codes. The specifics differ. The structural problem is identical: geometry is opaque to machines, but machines are the only scalable reviewers.

    The BIM Intent Compiler already compiles geometry from semantics. Every room width, corridor length, and egress distance is an arithmetic result, not a drawn line. That arithmetic is already in the database. The Standards Compliance module turns that arithmetic into a proof — one that a regulator can verify in minutes, not months.

    Where This Sits in the Pipeline¶

    INPUT: C_Order + C_OrderLine (compiled building)
       + AD_Val_Rule (jurisdiction rules, already seeded in ERP.db)
       + AD_Org_ID (active jurisdiction — MY, UK, SG, AU, UAE)
                ↓
Stage 1: COLLECT — query all elements from output.db by type
Stage 2: EVALUATE — apply AD_Val_Rule SQL against each element/space
Stage 3: CHAIN — topological sort (Kahn's algorithm, existing Inference Engine)
Stage 4: CERTIFY — emit ComplianceCertificate per space, per storey, per building
Stage 5: SIGN — spatial digest hash ties certificate to specific compilation
                ↓
OUTPUT: compliance_proof.db + compliance_report.json + submission_package/

    This is Stage 8.5 in the 9-stage pipeline — after ProveStage (Stage 8, which handles geometric proof) and before output packaging (Stage 9). It reads output.db. It writes compliance_proof.db. It never modifies the building.

    What Already Exists (Do Not Rebuild)¶

    The DocValidate spec already defines the infrastructure this module rides on. Read DocValidate §3 before implementing anything here.

    Existing Component What It Provides Reference
    AD_Val_Rule SQL-pattern rule table, jurisdiction-tagged DocValidate §1.2
    AD_Org_ID jurisdiction FK Active jurisdiction per compilation DocValidate §5
    Multi-jurisdiction seed data MY/UK/SG/AU room minimums DocValidate §11
    3-tier cascade Per-discipline → cross-discipline → vertical DocValidate §13
    Inference Engine Dependency DAG + proof tree + SKIP propagation BIM_Designer_SRS §14
    PlacementValidator 63 rules (33 building + 30 infra), already firing DocValidate §4
    ModelValidator pattern beforeSave/afterSave hooks DocValidate §1.3

    The Standards Compliance module is an orchestrator and certificate emitter, not a new rule engine. It calls AD_Val_Rule evaluations through the existing Inference Engine and packages the results into a submission-grade proof document. Do not duplicate rule evaluation logic.

    The Proof Chain — What Makes This Different¶

    A DocValidate pass is a database flag: val_result = PASS. Useful internally. Useless to a regulator.

    A compliance proof chain is a traceable record:

    BUILDING:  DemoHouse_MY_001
JURISDICTION:  MY (UBBL 1984, Amendment 2007)
COMPILED:  2026-03-27T14:32:01Z
LIBRARY_HASH:  a3f9c2...  (component_library.db)
SPATIAL_DIGEST:  5ddcd7...  (output.db tamper seal)

SPACE: BD_01 (Master Bedroom)
  Rule: UBBL s.43(1) — Habitable room minimum floor area
  Clause: "No room used for habitation shall have a floor area of less
           than 9.3 square metres"
  Measured:  floor_area = 14.82 m²   [EXTRACTED from output.db]
  Threshold:  9.3 m²                 [SOURCED from AD_Val_Rule id=102]
  Result:  PASS  (margin: +5.52 m²)
  Proof:  W-SC-ROOM-AREA-BD_01

SPACE: KT_01 (Kitchen)
  Rule: UBBL s.43(2) — Minimum kitchen dimension
  Clause: "No kitchen shall be less than 1.8 metres in any direction"
  Measured:  min_dimension = 2.1 m   [EXTRACTED from output.db]
  Threshold:  1.8 m                  [SOURCED from AD_Val_Rule id=103]
  Result:  PASS  (margin: +0.3 m)
  Proof:  W-SC-KITCHEN-DIM-KT_01

BUILDING RESULT: 47/47 rules PASS
CERTIFICATE:  SC-DemoHouse_MY_001-2026-03-27
REPRODUCIBLE: recompile from semantic file + library hash → same certificate

    Every value is extracted from output.db. Every threshold is sourced from AD_Val_Rule. Every citation names the statute, section, and clause verbatim. The margin is stated so reviewers know how close the edge case is. The spatial digest ties this certificate to exactly this compilation — change the building, the certificate is invalidated.

    Data Model¶

    New Tables (compliance_proof.db — separate from ERP.db and output.db)¶

    -- One row per evaluated rule per space
CREATE TABLE SC_Proof_Line (
    sc_proof_line_id  INTEGER PRIMARY KEY,
    sc_run_id         INTEGER NOT NULL REFERENCES SC_Run(sc_run_id),
    space_id          TEXT NOT NULL,         -- links to output.db element GUID
    ad_val_rule_id    INTEGER NOT NULL,       -- links to ERP.db AD_Val_Rule
    rule_code         TEXT NOT NULL,          -- e.g. "UBBL-S43-1"
    statute_ref       TEXT NOT NULL,          -- e.g. "UBBL 1984 s.43(1)"
    clause_text       TEXT NOT NULL,          -- verbatim clause (≤200 chars)
    measured_value    REAL NOT NULL,
    measured_unit     TEXT NOT NULL,          -- mm, m2, count, ratio
    threshold_value   REAL NOT NULL,
    threshold_dir     TEXT NOT NULL,          -- MIN or MAX
    result            TEXT NOT NULL,          -- PASS | FAIL | EXEMPT | PENDING
    margin            REAL NOT NULL,          -- measured - threshold (signed)
    proof_witness     TEXT NOT NULL,          -- W-SC-* witness ID
    skip_reason       TEXT                    -- if upstream rule failed (SKIP)
);

-- One row per compliance run (one run = one compilation + one jurisdiction)
CREATE TABLE SC_Run (
    sc_run_id         INTEGER PRIMARY KEY,
    c_order_id        INTEGER NOT NULL,       -- the compiled building
    ad_org_id         INTEGER NOT NULL,       -- jurisdiction (FK to ERP.db)
    jurisdiction_code TEXT NOT NULL,          -- MY | UK | SG | AU | UAE
    code_edition      TEXT NOT NULL,          -- e.g. "UBBL_1984_AMD2007"
    compiled_at       TEXT NOT NULL,          -- ISO8601 timestamp
    library_hash      TEXT NOT NULL,          -- component_library.db SHA256
    spatial_digest    TEXT NOT NULL,          -- output.db tamper seal hash
    total_rules       INTEGER NOT NULL,
    pass_count        INTEGER NOT NULL,
    fail_count        INTEGER NOT NULL,
    exempt_count      INTEGER NOT NULL,
    skip_count        INTEGER NOT NULL,
    overall_result    TEXT NOT NULL,          -- PASS | FAIL | PARTIAL
    certificate_id    TEXT UNIQUE             -- SC-{building}-{date} on PASS
);

-- Jurisdiction registry — what codes are loaded, their authority and edition
CREATE TABLE SC_Jurisdiction (
    sc_jurisdiction_id  INTEGER PRIMARY KEY,
    jurisdiction_code   TEXT UNIQUE NOT NULL, -- MY | UK | SG | AU | UAE | US_IBC
    full_name           TEXT NOT NULL,
    authority           TEXT NOT NULL,        -- CIDB | HSE | BCA | ABCB | MBAM
    primary_code        TEXT NOT NULL,        -- UBBL 1984 | Building Regs 2010
    current_edition     TEXT NOT NULL,
    effective_date      TEXT NOT NULL,        -- ISO date
    rule_count          INTEGER NOT NULL,
    status              TEXT NOT NULL         -- ACTIVE | DRAFT | PENDING
);

-- Rule-to-building-type applicability (not all rules apply to all types)
CREATE TABLE SC_Rule_Applicability (
    sc_rule_app_id    INTEGER PRIMARY KEY,
    ad_val_rule_id    INTEGER NOT NULL,
    building_type     TEXT NOT NULL,          -- RE | CO | IN | IN (infrastructure)
    space_type        TEXT,                   -- BD | KT | LR | WC | null=all
    min_storeys       INTEGER DEFAULT 1,
    max_storeys       INTEGER DEFAULT 99,
    mandatory         INTEGER NOT NULL DEFAULT 1  -- 1=mandatory, 0=advisory
);

    The Inference Engine Integration¶

    The Inference Engine (BIM_Designer_SRS §14) already implements dependency DAG + Kahn's topological sort. Standards compliance rules have the same dependency structure:

    ROOM_AREA (Rule 102) must PASS before
  OCCUPANT_LOAD (Rule 201) can evaluate, because
    EGRESS_CAPACITY (Rule 301) depends on OCCUPANT_LOAD.

If ROOM_AREA FAILS → OCCUPANT_LOAD is SKIPPED (not FAIL).
The proof chain records:
  Rule 201: SKIP — upstream Rule 102 FAILED (room area below minimum)
  Rule 301: SKIP — upstream Rule 201 SKIPPED

    This is not new code. ComplianceStageImpl calls InferenceEngine.evaluate() with a ComplianceRuleSet — the same interface DocValidate uses, filtered to jurisdiction-active rules and building-type-applicable rules only.

    // ComplianceStageImpl.java  — implementing BBC.md §8.5 Standards Gate
public class ComplianceStageImpl implements PipelineStage {

    public StageResult execute(CompilationContext ctx) {
        AD_Org_ID jurisdiction = ctx.getJurisdiction();   // from classify.yaml
        List<AD_Val_Rule> rules = ruleDAO
            .findActiveRules(jurisdiction, ctx.getBuildingType());

        // Topological sort — existing InferenceEngine
        List<AD_Val_Rule> ordered = inferenceEngine.sort(rules);

        List<SC_Proof_Line> proofs = new ArrayList<>();
        for (AD_Val_Rule rule : ordered) {
            if (inferenceEngine.isSkipped(rule, proofs)) {
                proofs.add(SC_Proof_Line.skipped(rule, "upstream FAIL"));
                continue;
            }
            double measured = ruleEvaluator.measure(rule, ctx.getOutputDb());
            ProofLine line = ProofLine.evaluate(rule, measured);
            proofs.add(line);
        }

        SC_Run run = SC_Run.from(ctx, proofs);
        proofDAO.persist(run, proofs);

        if (run.overall_result.equals("FAIL"))
            return StageResult.BLOCK("Compliance gate FAILED — " +
                run.fail_count + " rules. Promote blocked.");

        return StageResult.PASS(run.certificate_id);
    }
}

    DocAction Integration — The Promote Gate¶

    Compliance is a Promote gate, not a Save gate. The lifecycle:

    DRAFT       → user edits freely, no compliance check
IN_PROGRESS → DocValidate fires (geometric correctness, clash detection)
APPROVED    → Standards Compliance fires (regulatory proof chain)
COMPLETE    → Certificate issued, building locked
PROMOTE     → Certificate + semantic file + library hash submitted to authority

    A building cannot be Promoted without SC_Run.overall_result = PASS. This is enforced in DocActionImpl.canPromote(), not in UI validation. The compiler blocks at the data layer.

    APPROVED but compliance FAIL → PROMOTE button disabled
APPROVED and compliance PASS → PROMOTE button enabled
Certificate_ID stamped on C_Order.compliance_cert_id

    This mirrors how iDempiere blocks invoice posting without matching purchase order. The governance pattern is the same. The domain is different.

    Submission Package¶

    On PASS, the compiler assembles a submission package — a directory that a contractor hands to CIDB, HSE, BCA, or whichever authority:

    submission/
├── certificate.json          # SC_Run row — machine-readable
├── proof_chain.json          # All SC_Proof_Line rows — full evidence
├── building_semantic.yaml    # 10 KB source of truth (YAML + Order reference)
├── library_manifest.txt      # component_library.db hash + version
├── spatial_digest.txt        # output.db tamper seal
├── compliance_summary.pdf    # Human-readable — one page per jurisdiction
└── ifc_export.ifc            # Optional: IFC4 export for authority's own viewer

    The authority does not need to review the IFC. They verify the proof chain: 1. Take building_semantic.yaml + library_manifest.txt 2. Run the compiler 3. Check their output spatial_digest matches spatial_digest.txt 4. Rerun the compliance stage 5. Verify their certificate.json matches the submitted one

    Reproducible compliance. The authority becomes a verifier, not a reviewer. This is the regulatory workflow inversion described in StrategicIndustryPositioning §Machine-Provable Compliance.

    Witness Classes¶

    Witness What It Proves Gate
    W-SC-ROOM-AREA-{space_id} Floor area ≥ jurisdiction minimum Per space
    W-SC-ROOM-DIM-{space_id} Minimum dimension ≥ jurisdiction minimum Per space
    W-SC-CEILING-HT-{space_id} Ceiling height ≥ minimum for room type Per space
    W-SC-EGRESS-{storey_id} Egress path ≤ maximum travel distance Per storey
    W-SC-CORRIDOR-{id} Corridor width ≥ minimum Per corridor element
    W-SC-FP-SPACING-{zone_id} Sprinkler spacing ≤ maximum (FP discipline) Per FP zone
    W-SC-STAIR-WIDTH-{id} Staircase width ≥ minimum Per stair element
    W-SC-DISABLED-{id} Ramp gradient ≤ maximum, landing ≥ minimum Per ramp
    W-SC-VENTILATION-{space_id} Ventilation rate ≥ ASHRAE/UBBL minimum Per space
    W-SC-OCCUPANT-LOAD-{storey} Occupant load within egress capacity Per storey
    W-SC-BUILDING-CERT All mandatory rules PASS Building-level

    Each witness follows the existing pattern: ProofClass → evaluate() → WitnessRecord persisted to compliance_proof.db. Same infrastructure as BOMDigestVerifyTest and RoomValidityProof. No new witness machinery.

    Jurisdiction Activation — Configuration, Not Code¶

    The active jurisdiction is set in classify.yaml — the same file that defines building type and discipline scope:

    # classify_demohouse_my.yaml
building_prefix: DM
building_type: RE
jurisdiction: MY
code_edition: UBBL_1984_AMD2007
disciplines: [ARC, STR, ELEC, FP, ACMV]

    Changing jurisdiction: MY to jurisdiction: UK loads UK Building Regs rules from AD_Val_Rule where ad_org_id = UK. Zero code change. The rule set is data. The evaluator is the same.

    The same building, compiled twice with different jurisdictions, produces two certificates that can be compared. This is how a developer building in both Malaysia and the UK runs a single BOM against both code sets.

    Phase Sequence¶

    Phase SC-1 — Foundation (1 session)¶

    Extend AD_Val_Rule schema with statute_ref, clause_text, measured_unit, threshold_dir. Seed UBBL 1984 rules (15 residential rules, values EXTRACTED). Create compliance_proof.db schema. Wire ComplianceStageImpl into pipeline at Stage 8.5. Gate: W-SC-BUILDING-CERT fires for DemoHouse_MY, all 15 rules evaluated, proof chain written to compliance_proof.db.

    Phase SC-2 — Promote Gate (1 session)¶

    Wire DocActionImpl.canPromote() to check SC_Run.overall_result. Assemble submission package directory. Generate compliance_summary.pdf (tabular, one row per rule). Gate: DemoHouse_MY Promote blocked on FAIL, unblocked on PASS. Certificate ID stamped on C_Order.

    Phase SC-3 — Multi-Jurisdiction (2 sessions)¶

    Seed UK Building Regs Part A/B/M (20 rules, RESEARCHED). Seed SG BCA (15 rules, RESEARCHED). Extend SC_Jurisdiction table. Wire jurisdiction switching via classify.yaml. Gate: same DemoHouse compiled against MY, UK, SG produces three independent certificates.

    Phase SC-4 — Inference Chain (1 session)¶

    Wire InferenceEngine.sort() for compliance rules. Implement SKIP propagation where upstream FAIL causes downstream SKIP. Emit skip_reason on each skipped proof line. Gate: force a room area FAIL, verify occupant load and egress capacity are SKIPPED in the proof chain, not independently FAILED.

    Phase SC-5 — Infrastructure Codes (deferred)¶

    IFC4X3 infrastructure compliance: bridge load codes (Eurocode 1), road geometry standards (JKR Standard Specifications for Road Works), rail clearance gauges (KTMB standards). Follows same pattern — AD_Val_Rule rows, SC_Rule_Applicability for infra facility types. No engine changes required.

    Open Gaps (Honest)¶

    Gap Status Note
    MS 1184:2014 (Malaysian disabled access) PENDING Standard not freely available. Source from JKR or SPAN directly.
    UBBL Part VII fire egress travel distance (sprinkler-protected) PENDING Two values: 30m unprotected, 45m sprinkler-protected. Verify against 2007 amendment.
    UK Approved Doc B Vol.2 (non-residential) PENDING Different from Vol.1. Needed for IN building type.
    Occupant load calculation (assembly vs office vs residential) PENDING IBC Table 1004.5 — three different load factors. Needs space_type mapping.
    Dynamic egress graph (actual path length, not Euclidean) SPEC Requires I_Element_Connectivity (R22 in Open Gaps). Euclidean distance is a valid approximation until R22 is built.
    Digital signature on certificate DEFERRED PKI infrastructure. Certificate is tamper-evident via spatial digest today.

    Rule: All PENDING items must be resolved against the primary source document before being moved from DRAFT to ACTIVE in SC_Jurisdiction. No threshold value enters production as an assumption.

    What This Unlocks¶

    Once SC-1 through SC-4 are complete:

    For the Malaysia pilot: A DemoHouse compiled against UBBL produces a one-page compliance summary and a machine-verifiable certificate. A CIDB reviewer receives the submission package, runs three commands, and independently confirms the building passes 47 UBBL rules. Review time: minutes, not months.

    For the academic paper: The proof chain is a novel contribution — no prior BIM system produces machine-reproducible regulatory compliance evidence. The Inference Engine's SKIP propagation means failures are localised, not cascaded. The submission package is the artefact that justifies the "machine-provable compliance" claim in StrategicIndustryPositioning with concrete implementation evidence.

    For the competitive moat: Once one jurisdiction accepts a BIM Compiler submission package as a valid permit application, every contractor in that jurisdiction needs this pipeline. That is the adoption physics bypass.
