## KEY FINDING: Archive is probabilistic, not deterministic

The archive SVGs were generated by an LLM using training data knowledge of
TB-LKTN conventions. FLOOR and ROOF followed TB-LKTN closely → correct.
The 4 elevations did NOT follow TB-LKTN → broken output.

**Archive grading (TB-LKTN compliance):**

| View | Grade | Usable as reference? |
|------|-------|---------------------|
| FLOOR (A-01) | A | YES — Rosetta Stone reference |
| ROOF (A-06) | A | YES — Rosetta Stone reference |
| FRONT (A-02) | D | NO — no bay grids, broken level markers, arrowhead stubs |
| REAR (A-03) | D | NO — same defects |
| LEFT (A-04) | F | NO — no openings, no bay grids, same broken markers |
| RIGHT (A-05) | F | NO — same |

**Elevation defects (all 4 identical):**
- Zero vertical bay grids (A,B,C,D or 1,2,3)
- Level markers: arrowhead stubs go halfway from left, stop at building edge,
  don't connect to labels. No triangle symbol. Not dashed across full width.
- Only 3 levels (FFL, CEILING, RIDGE) — missing GRD, SILL, HEAD, EAVE
- Zero bay dimensions across top
- No scale bar
- Left/Right have no window/door openings at all

**Root cause:** The spec describes WHAT parts to draw but not HOW to construct
them. It says "level markers: triangle + dashed line" but doesn't specify
triangle direction, size, coordinates, dash pattern, label offset. The coder
(LLM or human) invents. FLOOR got it right because floor plan conventions
are well-known. Elevation conventions are less obvious → invention → garbage.

**Fix: Make the spec deterministic.** Every drawing part needs a construction
recipe in 2D.db — not prose in a markdown file. Three tables needed:

1. `2d_drawing_part` — WHAT each part is (triangle, polygon, dashed line...)
   with style values (stroke, fill, dasharray, font size)
2. `2d_part_placement` — WHERE each part goes per view type (zone: LEFT,
   RIGHT, TOP, BOTTOM, INSIDE) with anchor and offset rules
3. `2d_page_composition` — HOW pages are assembled: which parts on which
   page, spatial zones, draw order

When the coder reads: "ELEVATION + LEVEL_MARKER → zone=LEFT, anchor=level_z,
construction=triangle(left,3mm)+dashed_line(full_width,dasharray=6,2)+
label(offset=-2mm,format='{name}  {sign}{z:.3f}')" — there is only one
way to build it.

## ANTI-DRIFT: Consolidate specs before coding

The 2D module has specs scattered across 5 places:
1. `2D_Layout/docs/2D_ARCHITECTURAL_LAYOUT.md` — 1251 lines of prose
2. `2D_Layout/drawing_template.json` — formatting values
3. `2D_Layout/rosetta_2d.json` — Rosetta Stone rules
4. `2D_Layout/lib/input/2D.db` — 17 tables of style/label data
5. `internal/2DSpecToCode.md` — 133-item checklist

A coder reads the prose, misses the DB, hardcodes. Then the checklist says N
but doesn't say which DB table has the right value. Drift guaranteed.

**Consolidation rule:** The DB IS the spec. The prose is a reader's guide.

Before writing any code, the coder must:
1. Read `2D.db` tables for the part being implemented
2. Find the row that defines style/placement for that part + view type
3. If no row exists → spec gap → add to DB first, then code
4. Code reads from DB at runtime, never hardcodes
5. Checklist Y/N cites the DB table + column, not prose

The 3 new tables (`2d_drawing_part`, `2d_part_placement`,
`2d_page_composition`) close the gap between "what to draw" (existing tables)
and "how to construct it" (currently in prose or not at all).

Once these tables exist, the spec markdown shrinks to:
- §0-§1: principles (short)
- §2: process steps (short)
- §3: data source pointers (2D.db tables, not repeated content)
- §4-§8: REMOVED — replaced by DB queries
- §9: status + archive reference
- §10: test protocol

Everything the coder needs is `SELECT * FROM [2d_drawing_part] WHERE
view_type='ELEVATION' AND part_code='LEVEL_MARKER'` — not 50 lines of prose
that may or may not match the code.
