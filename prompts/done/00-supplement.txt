## Recommendation 1 — P10 threshold config (clears 6 buildings)

**Problem:** P10 SHAPE_IDENTITY uses a hardcoded planarity threshold (0.20) in
EyesConstants.java. 6 buildings fail because their IFC geometry slightly exceeds
this (TE facade panels at 0.2133, WA/ES/HI/SC/CS similar). These are not geometry
bugs — the shapes are valid, just slightly non-planar per the IFC modeller's choices.

**Fix:** Auto-compute the threshold from extraction statistics. During IFCtoBOM
extraction, compute the 95th-percentile planarity across all elements and write
it to `ad_sysconfig` in `*_BOM.db` (key: `P10_PLANARITY_THRESHOLD`). ProveStage
reads this at proof time. If absent, default stays 0.20. No YAML changes — the
threshold is data-driven from the IFC itself.

Alternative: raise the hardcoded default in EyesConstants.java from 0.20 to 0.25
(simpler, but less precise — may mask genuine issues in future buildings).

**Impact:** TE drops from 33,510 criticals to ~93 (residual P05/P06). WA, ES, HI,
SC, CS all clear. 6 buildings move from FAIL to PASS. Fleet: 214→220+ PASS.

**Spec ref:** EYES_SRS §4 proof configuration. EyesConstants.java.

**Effort:** Small — extraction stat + ad_sysconfig write + one threshold read.

## Recommendation 2 — Storey Z-band overlap fix (clears CA, helps CE)

**Problem:** CA (Clinic Architecture) has 726 of 2586 elements on "Unknown" storey.
PATTERN logs show FDN at Z=-1.0m and L1 at Z=-1.22m — they're *inverted*. The IFC
assigns elements to storeys by discipline containment, not by Z-height. The auto-
discovery algorithm (P127) sorts by minZ, which produces wrong ordering when the
IFC's storey Z-values overlap.

CA and CE are the same hospital model (different disciplines). One fix clears both.

**Fix:** Fix the `SpatialContainerConfig.discover()` algorithm itself. When storey
Z-ranges overlap (minZ of storey N+1 < maxZ of storey N), the algorithm should:
1. Detect the overlap condition from extraction element positions
2. Use IFC `rel_contained_in_space` storey assignment as primary (already in
   extracted.db since P125), Z-band as fallback only for orphan elements
3. No config — the algorithm decides based on data it already has

This is an algorithm fix, not a config addition. The IFC carries storey assignment;
discover() just needs to prefer it over Z-sorting when Z-bands conflict.

**Impact:** CA: 726 Unknown elements properly assigned → proof violations clear.
CE: already GREEN on gates but DRIFT=39,900 may resolve too.

**Spec ref:** DISC_VALIDATION_DB_SRS §10.4.13 (IFC-driven extraction).
PATTERN log: `pipeline_Clinic_Architecture_ifctobom_*.log` — FLOOR lines show overlap.

**Effort:** Medium — algorithm improvement in SpatialContainerConfig.discover().

## Recommendation 3 — RS P06 exemption (known, unfixable)

**Problem:** RS (Revit Structural) has 27,473 genuine P06 duplicates. Dense steel
framing in the IFC file places identical elements at identical positions. This is
how the IFC was authored — not a compiler bug.

**Fix:** Auto-detect during extraction. When IFCtoBOM finds >N elements at identical
positions (e.g., threshold: 1000 duplicates), write `P06_DUPLICATE_THRESHOLD` to
`ad_sysconfig` in `*_BOM.db`. ProveStage reads this and classifies violations above
the threshold as ADVISORY instead of CRITICAL. No YAML — the extraction data drives
the decision. RS's dense steel framing is self-evident from the extraction statistics.

Alternative: ProveStage auto-classifies P06 as ADVISORY when the violation count
exceeds 10% of total elements (RS: 27,473 / 472 = 58× — clearly a data pattern,
not a compiler bug). Zero config needed.

**Impact:** RS moves from FAIL to PASS. Fleet: +1.

**Spec ref:** EYES_SRS §4, TestArchitecture.md §G4.

**Effort:** Small — extraction stat or ratio check in ProveStage.

## Recommendation 4 — Infra furniture clash exemption (clears RD, RL)

**Problem:** RD (Road) and RL (Rail) are infrastructure buildings. They have no
furniture. The furniture clash check returns N/A → FAIL because zero furniture
elements means the check can't run, and the script treats that as failure.

**Fix:** In `rosetta_fidelity.sh` (or the clash check logic), return PASS when
the building has zero furniture elements. Infrastructure buildings don't have
furniture — the check is inapplicable, not failed.

**Impact:** RD and RL move from 6/7 to 7/7. Fleet: +2.

**Spec ref:** TestArchitecture.md §G4 clash check definition.

**Effort:** Tiny — one conditional in the shell script.

## Recommendation 7 — PATTERN summary in fleet output

**Problem:** PATTERN logging works (confirmed in pipeline logs) but the fleet
runner output doesn't surface it. To see storey assignment health, you must
read individual pipeline_*.log files. The CA "726 Unknown" problem was invisible
in the fleet summary.

**Fix:** After each building's IFCtoBOM run, grep the pipeline log for PATRN
FLOOR lines and emit a summary:
```
CA: 5 storeys, Unknown=726/2586 (28%) ← WARN
SH: 3 storeys, Unknown=26/58 (45%) ← expected (structural orphans)
```
Threshold for WARN: Unknown > 30% AND Unknown > 100 elements (avoids false
positives on small buildings like SH where structural orphans are normal).

**Impact:** Fleet-level visibility into storey assignment quality. No gate change.

**Spec ref:** DISC_VALIDATION_DB_SRS §10.4.10 PATTERN logging channel.

**Effort:** Small — shell script grep + printf.

## YAML dependency audit (2026-03-31)

**Rule:** YAML is Order input only. No extraction config, no compilation config,
no spatial coordinates. P125→P127→P129 unbuckled extraction from YAML.

### Violations found — actively consumed by ClassificationYaml.java

| Key | YAML files | Java line | Nature |
|-----|-----------|-----------|--------|
| `geometry_fail_threshold` | TE (=2), MO (=1) | ClassificationYaml:326 | Extraction config disguised as Order input |
| `origin_m` | FK (7), IN (73), DM (5) | ClassificationYaml:216 | Legacy scope box world coordinates |
| `aabb_mm` | FK (7), IN (73), DM (5) | ClassificationYaml:212 | Legacy scope box bounding volumes |

**No other violations.** `bom_category`, `doc_base_type`, `p06_exempt` all absent.
The P122 rename and S84 drop are clean across all 35 YAMLs.

### Analysis

**`geometry_fail_threshold`:** Pure config leak. TE allows 2 mesh mismatches, MO
allows 1. These control how many geometry QA failures IFCtoBOM tolerates before
aborting. Should move to `ad_sysconfig` in `*_BOM.db` — either auto-computed from
extraction statistics (count elements with no library mesh match) or as a migration
seed value. Removal from YAML requires updating ClassificationYaml record to drop
the field and having BomValidator read from ad_sysconfig instead.

**`origin_m` / `aabb_mm`:** These are the ScopeBomBuilder fallback for buildings
without IFC `rel_contained_in_space` data. P125 added the IFC path and cleaned
SH + DX, but three buildings still depend on scope boxes:

- **FK:** 0 IfcSpace rows in extraction DB. 7 rooms defined by scope boxes.
  Cannot remove until FK extraction DB has IfcSpace data — either the IFC
  file lacks IfcSpace entities, or extract.py doesn't extract them for FK.
- **IN:** 73 rooms across 5 storeys defined by scope boxes. Same question —
  does the IN IFC file have IfcSpace entities? If yes, extract.py should
  populate `rel_contained_in_space` and the scope boxes become removable.
  If no, ScopeBomBuilder's AABB fallback is the only option until Order-time
  scope definition exists (BIM Designer future work).
- **DM:** GENERATIVE building. Scope boxes define the generative room layout.
  Different contract — DM doesn't extract from IFC, it generates from the
  YAML recipe. For generative buildings, room coordinates ARE Order input
  (the designer is defining the building). DM may be a legitimate exception.

### Remediation path

| Fix | Effort | Prerequisite |
|-----|--------|-------------|
| Move `geometry_fail_threshold` to ad_sysconfig | Small | R1 implementation (auto-compute or seed) |
| Remove FK scope boxes | Medium | Verify FK IFC has IfcSpace; if not, populate or accept fallback |
| Remove IN scope boxes | Medium | Verify IN IFC has IfcSpace; 73 rooms is substantial migration |
| DM scope boxes | None | Generative = legitimate Order input. Room coords define the design |

### Verified results (2026-03-31)

Checked `rel_contained_in_space` row counts in extraction DBs:

- **FK** (`Ifc4_FZKHaus_extracted.db`): **0 rows**. The IFC file has no IfcSpace
  entities. Scope boxes are the only room assignment path. Cannot remove until
  either: (a) the IFC is re-authored with IfcSpace, or (b) Order-time scope
  definition exists (BIM Designer future). FK scope boxes are a **legitimate
  fallback**, not drift.
- **IN** (`Ifc2x3_AC11Institute_extracted.db`): **253 rows**. The IFC HAS
  IfcSpace data. The 73 scope boxes in classify_in.yaml are **dead code** —
  ScopeBomBuilder should be reading from rel_contained_in_space, same as SH.
  These can be removed once IN is verified to pass with IFC-driven assignment.
- **DM**: GENERATIVE — no extraction DB. Room coordinates ARE the design.
  Legitimate Order input.

### Recommendation

1. **Immediate (R1 scope):** Remove `geometry_fail_threshold` from TE/MO YAMLs
   when R1 moves threshold to ad_sysconfig. One change, two files.
2. **IN cleanup (medium):** Remove 73 `origin_m`/`aabb_mm` entries from
   classify_in.yaml. Add `ifc_space` mappings instead (253 IfcSpace rows
   available). Verify IN still passes 7/7 with IFC-driven assignment.
3. **FK stays:** 0 IfcSpace in IFC file. Scope boxes are the only option.
   Accepted fallback — document as legitimate.
4. **DM exception:** Generative buildings use YAML room coordinates as Order
   input. Not a violation — different contract.
5. **ClassificationYaml.java:** After IN migrates, the `origin_m`/`aabb_mm`
   parsing path serves only FK and DM. Keep as fallback, but guard with a
   log warning when scope boxes are used for EXTRACTED buildings (flags any
   future drift).
