## C) Fix generated 4D schedule quality (Z support rule + frontier mass)  ← suggested FIRST
Two symptoms, ONE root cause = the heuristic schedule in `injectGantt()` (`time_machine.js`,
Pass-1 structural loop) orders by Z-band (3m) + trade seq (footing→column→beam→slab) +
"structural band N waits for band N-1", with **no geometric support dependency** and **no
concurrency control**:
- **(c1) Floating beams:** beams/slabs play in before the columns directly beneath them.
  ⚠ ROOT CAUSE CONFIRMED (read origin/main injectGantt 2348-2520): elements are banded by
  **center-Z** (`Math.floor(cz/3)`, line ~2361), sorted band→seq→cz, and the only vertical
  dependency is "structural band N waits for band N-1" (`bandDone[el.band-1]`). A thin beam sits
  at the storey TOP while its supporting column is CENTERED mid-storey — so the column's center-Z
  often quantizes into the SAME or a HIGHER band than the beam it carries → the beam is scheduled
  before its support → floats. NOTE: this is NOT the template's doing — the generative timing in
  `time_machine.js` consumes only `matchRule(cls).{sequence,phase,resource,productivity}`; the
  template's `predecessors` array is **never read**, so editing `4D_schedule_common.json` cannot
  fix it. Fix = an element-level supported-by rule: an element waits for the structural elements
  geometrically below-and-overlapping it (or, cheap partial: band columns by TOP-Z / beams by
  BASE-Z so a beam can't precede a column whose top reaches it).
- **(c2) Yellow-cube mass:** the TM construction-frontier markers (3m yellow wireframe boxes,
  `time_machine.js:744-751`) show "en masse for a long duration." INVESTIGATED — NOT a leak:
  cleanup is correct (`renderAtTime → clearHighlight → clearAllOutlines` every tick) and
  `end_ts` is populated (`loadOps` line 62, `params._end_ts` + fallback, cache path preserves
  it). The mass is the GENUINE frontier being fat/slow because the schedule over-parallelizes
  with long overlapping install windows. Fix: tighten concurrency / scale durations so the
  frontier is a thin moving wave, not a blob.
- Add witnesses: `§FRONTIER_COUNT` per tick (prove it thins after the fix) and a guard/log for
  any op with `end_ts > _projectEnd` (would pin a cube yellow forever — verify none exist).
- **(c3) Generated-after-captured:** another session staged (not pushed) "generated MEP/ARC
  start after captured structure per storey" — same family, do it WITH c1/c2 so the generated
  fill respects both the captured structure and the support order.
