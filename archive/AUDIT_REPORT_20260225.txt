# BIM Intent Compiler

A compiler that transforms declarative building descriptions into spatially validated BIM models — elements placed at mathematically proven coordinates, backed by a three-database ERP architecture modelled on iDempiere's C_Order/M_BOM/CO pipeline.

## What It Actually Does (Honest Assessment)

The compiler reads a DSL manifest + relational metadata (room boundaries, wall faces, BOM assembly trees) and computes element positions. It produces a SQLite database containing walls, doors, windows, slabs, furniture, MEP, and structural elements with spatial indexing (R*Tree).

**What is proven by maths (170 tests, 13 geometry audits):**

- SampleHouse: 56 elements, all centroids match IFC reference to <50mm. 98% LOD400 mesh (55/56).
- Duplex: 1,089 elements, all centroids match reference to <50mm. Two-storey Z separation verified (L2 furniture at Z=3.0m). 6% LOD400 mesh (66/1089 — furniture only; walls/MEP/structural use generated boxes).
- Terminal: 51,088 elements placed via legacy flat coordinate copy (tautological — reads extracted positions back). Pending relational migration.

**What is NOT proven:**

- Generative placement from intent only (TB-LKTN is the test case, Phase RM-4, not yet done)
- Visual correctness (no rendering validation — all proofs are coordinate/centroid maths)
- LOD400 geometry for DX non-furniture elements (94% are parametric boxes with correct dimensions but no real mesh)
- Material assignment for BOM-dispatched furniture (NULL material_rgba — known debt)

## Architecture

### Three-Database Separation (iDempiere ERP Model)

```
component_library.db          {PREFIX}_BOM.db                    Output DBs
═══════════════════           ══════                    ══════════
M_Product (ad_product_dim)    M_BOM (m_bom)             CO_EmptySpace (header)
  57 products, dims in m        50 BOMs, 14 categories    CO_EmptySpaceLine (per-storey)
  Clearances, host rules        201 BOM lines             elements_meta + elements_rtree
C_OrderLine (ad_element_rule)   425 attributes            base_geometries
  1,263 placement rules       M_BomCategory (14 codes)    spatial_structure
C_Order (ad_building_registry)  3 dimensions:
  4 buildings registered          Category (LI/BD/KT/...)
ad_room_boundary (60 rooms)       Owner (SH/DX/TB/TE)
ad_wall_face, ad_building_grid    SpaceSize (AABB mm)
```

### Two Placement Paths

| Path | Buildings | How It Works | Fidelity Claim |
|------|-----------|-------------|----------------|
| **Relational** | SH (43 rules), DX (1,026 rules), TB (64 rules) | `RelationalResolver` computes positions from `ad_element_rule` + `ad_room_boundary` + `ad_wall_face`. Wall fractions, room fractions, BOM tree expansion. Real maths. | Genuine — coordinates computed, not copied |
| **Legacy Flat** | Terminal (51,088 rows) | `PlacementAD.loadLegacyFlat()` reads pre-extracted coordinates from `ad_element_placement`. Direct copy. | Tautological — compares output against its own input |

The relational path is the target architecture. SH and DX prove that a building can be decomposed into relational rules (grid, rooms, wall faces, placement fractions) and recomposed to match the IFC reference within 50mm. Terminal awaits migration to relational rules (Phase RM-5b).

### Compilation Pipeline

```
DSL manifest → BuildingParser → BuildingCompiler → StoreyCompiler
                                                        ↓
                                    RelationalResolver (computes from rules)
                                    FurnitureBOMResolver (expands BOM trees)
                                                        ↓
                                    PlacementAD (cache layer)
                                                        ↓
                                    BuildingWriter → ElementPersistence → Output DB
                                                        ↓
                                    PlacementProver (IsAvailable quality gate)
                                    WitnessGenerator (mathematical proofs)
```

### BOM Assembly Model (6-Level Hierarchy)

```
UNIT (UN)           DUPLEX_UNIT_STD         ← C_Order (building)
  └─ FLOOR (L1/L2)   FLOOR_DX_L1_STD       ← dz=0mm
  └─ FLOOR (L2)      FLOOR_DX_L2_STD       ← dz=3000mm (proven by test R3)
     └─ ROOM (LI)      LIVING_SET          ← dispatched by room_type + area
        └─ SET (FR)       SOFA_AREA         ← furniture group
           └─ ITEM        Sofa, Piano       ← leaf product from ad_product_dim
```

Each level is an `m_bom` record. Children are `m_bom_line` with dx/dy/dz offsets in metres, `rotation_rule`, and `SpaceSize` (AABB in mm). Buffer children (category=ST) fill gaps. Critical invariant: `Parent.SpaceSize = SUM(children.SpaceSize)` per axis.

## Geometry Fidelity Breakdown

| Building | Elements | LOD400 Mesh | GEN-BOX | LOD400 % | Position Match |
|----------|----------|-------------|---------|----------|----------------|
| SampleHouse | 56 | 55 | 1 | **98%** | 100% <50mm |

| Terminal | 51,088 | — | — | flat copy | tautological |

**SH** has near-complete LOD400 geometry — real IFC meshes extracted and matched.
**DX** has correct positions for all 1,089 elements but 94% use parametric box geometry. The furniture (66 items) has real LOD400 mesh; walls, doors, windows, MEP, and structural elements use axis-aligned boxes with correct dimensions.
**Terminal** reads pre-extracted coordinates directly — not yet on the relational path.

## First-Principles Audit Results

**No cheating found in the pipeline code:**

- Zero hardcoded coordinates in `RelationalResolver`, `StoreyCompiler`, `BuildingWriter`
- Zero building-specific if/switch statements (no `if buildingType == "SH"`)
- Zero TODO/FIXME/HACK/WORKAROUND/TRANSITIONAL markers in main source
- `RelationalResolver.computeOne()` genuinely computes positions from wall fractions, room fractions, and BOM offsets — not a copy operation
- All dimensions read from `ad_product_dim` (metres), `ad_element_rule` (mm), `ad_room_boundary` (mm)

**Architectural honesty:**

- The relational rules (ad_element_rule, ad_room_boundary, ad_wall_face) were *extracted* from the same IFC reference used for validation. So the claim is: "Can we decompose an IFC building into relational rules and faithfully recompose it?" The answer is yes for SH/DX. This is not the same as "Can we generate a novel building from scratch?" — that requires TB-LKTN (Phase RM-4).

## CO_EmptySpace Pipeline (Phase 4)

The compiler produces warehouse allocation records following the iDempiere CO (Completion) pattern:

```
co_empty_space (header)          co_empty_space_line (children)
  building_id                      bom_id, bom_line_role
  bom_owner (SH/DX/TB/TE)         bom_level (0=UNIT, 1=child)
  doc_status (DR→IP→CO/RE)        storey_name
  is_available (0=allocated)       before_z_mm, next_z_mm
  aabb_width/depth/height_mm       aabb dimensions
```

SH: 1 header + 4 lines (UNIT, GROUND_SLAB, Ground Floor, ROOF)
DX: 1 header + 6 lines (UNIT, GROUND_SLAB, Ground, UPPER_SLAB, Upper, ROOF)

Quality gate: `IsAvailable` proof stage transitions IP→CO on success (all element proofs pass), IP→RE on critical violations.

├── DAGCompiler/                    ← Compiler module (main pipeline)
│   ├── src/main/java/com/bim/compiler/
│   │   ├── dsl/                    ← Core: parser, StoreyCompiler, RelationalResolver,
│   │   │                             PlacementAD, BuildingWriter, ElementPersistence
│   │   ├── library/                ← FurnitureBOMResolver, ComponentLibrary
│   │   ├── geometry/               ← BoundingBox, Point3D, Mesh
│   │   ├── bom/                    ← BOM expansion, PhantomLayout
│   │   ├── validation/             ← PlacementProver, GeometryIntegrityChecker
│   │   └── contract/               ← 6-layer contract interfaces
│   ├── lib/input/                  ← Reference DBs (Rosetta Stones)
│   └── lib/output/                 ← Compiled output DBs (generated)
├── ORMSandbox/                     ← iDempiere-style PO layer + BuildingInspector
│   └── src/main/java/com/bim/ormsandbox/po/  ← X_M_BOM, MBOMLine, M_AdElementRule, etc.
├── TopologyMaker/                  ← Generative building pipeline (UBBL-compliant)
├── orm-core/                       ← BasePO + ModelQuery framework
├── library/

├── migration/                      ← SQL migration scripts (idempotent)
└── docs/                           ← Architecture docs (see below)
