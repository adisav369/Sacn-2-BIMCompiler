    Spatial ERP OOTB — Every Record Has a Place¶

    The leap: ERP is not forms and menus. ERP is space. A warehouse has aisles. An office has cabinets. A factory has stations. A phone has a swipe. Put them together: swipe through your business like swiping through a building.

    1. The Thesis¶

    Three.js + SQLite + one browser already renders buildings with 10,000 elements, runs clash detection, tracks changes, computes costs — all with zero install.

    The same engine renders anything with coordinates:

    What users see What the engine sees
    A warehouse with racks Products in a BOM hierarchy with xyz
    A store with shelves Products in a BOM hierarchy with xyz
    A factory with machines Products in a BOM hierarchy with xyz
    An office with filing cabinets Products in a BOM hierarchy with xyz
    A logistics network with hubs Products in a BOM hierarchy with xyz

    The BOM is universal. Container → sub-container → item, recursively. The renderer doesn't know it's drawing a cabinet instead of a wall. The document engine doesn't know it's processing a pick order instead of a construction order. Same five tables. Same state machine. Same journal.

    2. The Three Experiences¶

    2.1 Desktop — The God View¶

    Full 3D scene. Orbit, pan, zoom. Click any object to open its document. Colour-code by status (draft=grey, in-progress=blue, overdue=red, completed=green). This is the planner's view — the person who designs the layout and manages operations.

    Already exists: the BIM OOTB viewer. Extend, don't rebuild.

    2.2 Mobile — The Swipe View¶

    The killer UX. The scene becomes a card stack:

    • Swipe right → next location / zone / aisle (spatial navigation)
    • Swipe left → previous
    • Swipe up → drill into container (warehouse → aisle → rack → bin)
    • Swipe down → back up one level
    • Tap → open the document / act on it (approve, pick, count, complete)

    Each card shows: - A mini 3D thumbnail of the location (pre-rendered or live Three.js) - The key numbers (items in zone, pending picks, value, alerts) - Action buttons (context-dependent: Pick, Putaway, Count, Approve)

    This is the TikTok model applied to ERP: infinite vertical scroll through your business, each card is a spatial snapshot with actionable context. The user never sees a form. They see a place.

    2.3 Walk View — AR-lite¶

    Phone camera + GPS/beacon → overlay pick instructions on the actual aisle. Phase 3. But the data model supports it from day 1 because every item already has coordinates. When the tech is ready, the data is already spatial.

    3. Domain Catalog¶

    3.1 WMS — Warehouse Management¶

    Spatial object ERP record User action
    Warehouse Organization / Plant Select facility
    Zone (receiving, storage, shipping) Locator group Swipe between zones
    Aisle Locator level 1 Swipe down into zone
    Rack / Shelf Locator level 2 Visual pick path
    Bin Locator level 3 (x, y, z) Tap to pick / putaway
    Pallet / SKU Product at locator The item being moved

    Documents: Goods Receipt, Pick Order, Putaway, Movement, Physical Count, Shipment.

    Visual power: Heat map of bin utilization. Red = full, green = empty. Pick path lights up as a glowing route through the 3D warehouse. Putaway suggests the nearest empty bin by highlighting it.

    3.2 POS — Point of Sale / Retail¶

    Spatial object ERP record User action
    Store Organization Select store
    Zone (entrance, checkout, aisles) Area grouping Swipe between zones
    Aisle / display Fixture Tap to see products
    Shelf position Planogram slot Drag product to rearrange
    Product facing Product + qty Sales data overlay

    Documents: Sales Order (auto-completed), Restock Order, Planogram Change, Inventory Count.

    Visual power: Products glow by sales velocity. Dead stock turns grey. Manager swipes through aisles, sees what's selling, drags to rearrange. Planogram changes become kernel_ops — undo/redo, share, replay.

    3.3 MFG — Manufacturing / Shop Floor¶

    Spatial object ERP record User action
    Factory Plant Select facility
    Production line Work center group Swipe between lines
    Station Work center Tap to see work order
    Machine / fixture Resource Status overlay
    WIP item Production order line Move to next station

    Documents: Work Order (BOM explosion), Material Issue, Production Receipt, Quality Check.

    Visual power: Stations colour-coded by status (idle/running/blocked/maintenance). Bottleneck = red glow. Supervisor swipes through the floor, sees the constraint, taps to reassign. Same kernel_ops log = same undo/redo.

    3.4 Logistics — Network / Fleet¶

    Spatial object ERP record User action
    Network map Organization tree Overview
    Hub / depot Warehouse / plant Swipe between hubs
    Dock door Receiving point Tap to see inbound
    Vehicle Resource / asset Track location
    Shipment M_InOut Status + route

    Visual power: Map view (2D) with 3D hub drill-down. Shipments animate along routes. Late = red. Click hub → see the 3D warehouse inside. Nested spatial contexts, infinitely deep.

    3.5 F&B — Restaurant / Café / Food Court¶

    The most human-facing domain. Proves the schema works where the "container" is a dining table and the "item" is a meal.

    Spatial object ERP record User action
    Restaurant Organization Home view
    Zone (patio, main hall, private) Locator group Swipe between zones
    Table Container (with seat capacity) Tap to open / take order
    Guest / cover Item at container Dietary info, tab total
    Order Document (SALES_ORDER) Draft → Sent → Served → Settled

    Documents: Sales Order (the meal), Invoice (the bill), Payment (settlement).

    The waiter's swipe flow: Walk the floor. Swipe through tables. Each card shows: table number, occupancy, order status, wait time. Red glow = "Table 4 waiting 12 minutes for drinks." Tap → add items → send to kitchen. Swipe to next table. The waiter never touches a POS terminal.

    Kitchen display = station-filtered card stack. Cook sees only orders at their station (grill, cold, dessert). Each card = one order's items for that station. Tap to mark "plating." Waiter's card updates instantly (blue pulse → green). Same document_lines, filtered view.

    Visual power: Table utilization heat map. Average turn time per zone. Which waiter is lagging (amber glow on their tables). Manager sees the whole restaurant as a living organism from the Map Room.

    3.5.1 QR Code — Customer as Read-Only Viewer¶

    Customer scans QR at table → browser opens their personal spatial view of that container, filtered by token:

    ┌─────────────────────────────────┐
│  ┌───────────────────────────┐  │
│  │     Your Table (3D)       │  │  Mini scene of their table
│  │     ○  ○  ○  ○            │  │  (covers, place settings)
│  └───────────────────────────┘  │
│                                 │
│  Table 7 — 4 guests             │
│                                 │
│  Appetizers    ✅ served         │
│  Mains         ⏳ preparing     │  Real-time status from
│  Drinks        ✅ served         │  document_lines.metadata
│                                 │
│  Running total: RM 145.00       │
│                                 │
│  [ Request Bill ]               │  Tap → INVOICE created
│  [ Pay Now ]                    │  Tap → payment gateway
└─────────────────────────────────┘

    How it works: - QR encodes a token that maps to one container (the table) - The .db is filtered: customer sees only their table's document_lines - No login. No app download. No account. Just scan and see. - "Pay Now" triggers doc_status transition: IN_PROGRESS → COMPLETED - Journal auto-generates: debit CASH_BANK, credit REVENUE_FOOD / REVENUE_DRINK

    The customer never flags down a waiter to ask "is our food coming?" They see the moment the cook marks "plating." Settlement happens without a card machine coming to the table. Lower touch, faster turn, better margin.

    3.5.2 Banking Settlement — Document Completion¶

    Payment completes the document. The journal posts automatically:

    Order #0047 → COMPLETED

| account        | debit  | credit |
|----------------|--------|--------|
| CASH_BANK      | 145.00 |        |
| REVENUE_FOOD   |        | 110.00 |
| REVENUE_DRINK  |        |  35.00 |

    Kitchen sees the order move to PAID (no food held for walkouts). Waiter sees the table released (green → grey). Next guest can be seated. Owner's Map Room P&L updates in real time.

    Payment mechanism: Web Payment Request API (Stripe, local bank redirect, e-wallet). Zero-install: no app, no SDK beyond what the browser provides. Offline fallback: waiter marks COMPLETED manually (cash), reconciliation on next sync.

    3.5.3 The Full Role Stack¶

    Role Device Mode Container scope Actions
    Owner Desktop Map Room (3D) Whole restaurant Set prices, view P&L, floor plan edit
    Manager Tablet Map Room Zones + tables Open/close sections, reassign waiters
    Waiter Phone Swipe Assigned tables Take order, mark served
    Customer Phone (QR) Read-only swipe Their table only Track order, request bill, pay
    Cook Tablet Swipe (station filter) Orders by station Mark items complete

    Same five tables. Same state machine. Same journal. Five different people looking at the same data through different spatial filters.

    3.5.4 Customer Self-Order (Phase 2)¶

    Phase 1: read-only + payment. Phase 2: customer can request items: - Customer taps "Add beer" → kernel_op logged with user_tag = 'QR_TOKEN_xxx' - Waiter gets notification: "Table 7 requested 2 Tiger Beer — pending approval" - Waiter approves → item added to order. Rejects → customer sees "declined." - Request-approve pattern prevents abuse (wrong table, impossible items)

    3.6 Back Office — The Spatial Desktop¶

    This is the radical one. Documents become physical objects.

    Spatial object ERP record User action
    Office User's workspace Home view
    Cabinet Document type (AP, AR, GL, HR) Swipe between departments
    Drawer Period / status / category Swipe down to filter
    Folder Batch / business partner Tap to open
    Document Invoice, payment, journal Act on it

    The metaphor: An accountant opens their office. Four cabinets: Payables, Receivables, General Ledger, Payroll. The Payables cabinet has a red glow — 3 overdue invoices. Swipe into it. Three drawers: This Week, This Month, Older. Open This Week. Three folders, one per vendor. Tap the red one. See the invoice. Approve. Swipe back.

    No menu. No list. No search. The user navigates spatially, the same way they'd walk to a filing cabinet. The urgency heatmap (red/amber/green) replaces dashboards. The spatial memory replaces bookmarks.

    Visual power: Cabinet size = volume of records. Drawer thickness = value. Red glow = action needed. The user's peripheral vision does what 47 dashboard widgets try to do — show what needs attention, where it is, how big it is.

    4. Universal Schema — Five Tables¶

    All domains share the same schema. No domain-specific tables.

    -- Container hierarchy (recursive BOM, any depth)
-- A warehouse, a cabinet, a production line — all the same structure
CREATE TABLE containers (
    id          TEXT PRIMARY KEY,
    parent_id   TEXT REFERENCES containers(id),
    name        TEXT NOT NULL,
    category    TEXT,           -- ZONE, AISLE, RACK, BIN, CABINET, DRAWER, STATION...
    geometry_id TEXT,           -- FK to component_geometries (3D shape)
    x REAL, y REAL, z REAL,    -- position within parent
    metadata    TEXT            -- JSON: capacity, status, custom fields
);

-- Items that live in containers
-- A product on a shelf, a document in a drawer, a machine at a station
CREATE TABLE items (
    id           TEXT PRIMARY KEY,
    container_id TEXT REFERENCES containers(id),
    product_ref  TEXT,          -- what this item IS (SKU, doc type, machine model)
    name         TEXT,
    qty          REAL DEFAULT 1,
    geometry_id  TEXT,          -- 3D shape (optional — not all items are visual)
    x REAL, y REAL, z REAL,    -- position within container
    metadata     TEXT           -- JSON: serial, lot, expiry, status, custom
);

-- Documents (orders, receipts, movements, invoices — all the same)
CREATE TABLE documents (
    id          TEXT PRIMARY KEY,
    doc_type    TEXT NOT NULL,  -- PICK_ORDER, WORK_ORDER, SALES_ORDER, INVOICE...
    doc_status  TEXT DEFAULT 'DRAFT',  -- DRAFT | IN_PROGRESS | COMPLETED | VOIDED | REVERSED
    created     TEXT NOT NULL,
    completed   TEXT,
    description TEXT,
    metadata    TEXT            -- JSON: vendor, customer, priority, custom
);

-- Document lines — each line references an item at a location
CREATE TABLE document_lines (
    id          TEXT PRIMARY KEY,
    doc_id      TEXT REFERENCES documents(id),
    item_id     TEXT REFERENCES items(id),
    container_id TEXT REFERENCES containers(id),
    qty         REAL,
    unit_price  REAL,
    metadata    TEXT            -- JSON: lot, serial, notes
);

-- Journal — auto-generated on document completion
CREATE TABLE journal (
    id          TEXT PRIMARY KEY,
    doc_id      TEXT REFERENCES documents(id),
    line_id     TEXT REFERENCES document_lines(id),
    account     TEXT,           -- MATERIAL | LABOUR | OVERHEAD | REVENUE | COGS
    debit       REAL DEFAULT 0,
    credit      REAL DEFAULT 0,
    timestamp   TEXT
);

    Plus the existing tables that carry over unchanged: - kernel_ops — change log, undo/redo, replay (add user_tag column) - component_geometries — 3D shapes for any domain - project_metadata — key/value store for project-level config

    5. State Machine — One for All Documents¶

         ┌─────────┐
     │  DRAFT  │──────── user creates or auto-generates
     └────┬────┘
          │ start
     ┌────▼──────────┐
     │  IN_PROGRESS  │──────── work happening (picking, producing, approving)
     └────┬──────────┘
          │ complete
     ┌────▼──────────┐
     │  COMPLETED    │──────── journal entries auto-generated
     └────┬──────────┘
          │ reverse (error correction)
     ┌────▼──────────┐
     │  REVERSED     │──────── counter-journal entries auto-generated
     └──────────────┘

     Any state except COMPLETED/REVERSED:
          │ void
     ┌────▼──────────┐
     │   VOIDED      │──────── cancelled, no journal impact
     └──────────────┘

    Every transition is a kernel_op. Full audit trail. Undo = reverse the transition.

    6. The Swipe UX Spec¶

    6.1 Navigation Model¶

    The spatial hierarchy maps to swipe gestures:

    Swipe RIGHT  →  next sibling   (Aisle 1 → Aisle 2 → Aisle 3)
Swipe LEFT   →  prev sibling   (Aisle 3 → Aisle 2 → Aisle 1)
Swipe UP     →  drill in       (Aisle → Rack → Bin)
Swipe DOWN   →  back out       (Bin → Rack → Aisle)
TAP          →  act            (open document, confirm pick, approve)
LONG PRESS   →  inspect        (full detail card, 3D preview, history)

    6.2 Card Layout¶

    Each swipe-card:

    ┌─────────────────────────────────┐
│  ┌───────────────────────────┐  │
│  │                           │  │
│  │     3D Thumbnail          │  │  Top 60%: mini Three.js scene
│  │     (live or cached)      │  │  or pre-rendered snapshot
│  │                           │  │
│  └───────────────────────────┘  │
│                                 │
│  Aisle 3 — Zone B              │  Location breadcrumb
│  ▓▓▓▓▓▓▓░░░  68% full         │  Capacity / utilization bar
│                                 │
│  🔴 3 picks pending            │  Alert / action summary
│  🟢 12 items in stock          │  (colour = urgency)
│                                 │
│  [ Pick ]  [ Count ]  [ Move ] │  Context actions
└─────────────────────────────────┘

    6.3 Heatmap Overlay¶

    In 3D view (desktop) or card thumbnails (mobile), objects colour by status:

    Colour Meaning
    Red glow Action needed / overdue / blocked
    Amber Approaching threshold (low stock, due soon)
    Green OK / completed / available
    Grey Inactive / empty / not relevant to current task
    Blue pulse In progress (someone working on it)

    The user's eye is drawn to red. No dashboard needed.

    7. POC First — All-in-One Device¶

    7.1 The POC Principle¶

    The maker IS the user. The seller IS the buyer. One phone. One .db.

    The POC doesn't separate roles across devices or networks. One person experiences the entire flow on one device: set up the restaurant floor plan, take an order as waiter, see the kitchen queue, view it as the customer, settle the bill. All roles, all swipe directions, one browser, one session.

    This is exactly how BIM OOTB was proven — one person drops an IFC file, sees the 3D scene, runs clash detection, exports a BOQ. The single-user experience IS the product. Multi-user is a deployment choice, not a feature dependency.

    Why this works as a demo: The person watching the POC sees ALL roles in 60 seconds. They don't need to imagine "what the customer would see" — they see it. They don't need a second phone — they swipe between perspectives. The power is in the data model, not the network topology.

    7.2 The Two-Step Path¶

    Step 1: POC (now)                    Step 2: Deployed system (when ready)
─────────────────                    ──────────────────────────────────────
One phone, one .db                   .db on OCI bucket (you already do this)
All roles on one device              ?scope= filters per role
Maker = user                         Owner shares links/QR codes
Edit + view in same session          Cloud relay: edits sync via bucket
No server, no cloud                  Same OCI setup as BIM OOTB today

    Step 2 is NOT a rebuild. It's the same .db, same viewer, same swipe UI — just uploaded to a bucket and shared via URL, exactly like BIM OOTB share links already work. The ?scope= and ?mode= parameters are already in the URL — they just become meaningful when multiple people access the same data.

    7.3 Cloud Relay (Step 2 — when needed)¶

    When the user is ready to separate maker from consumer:

    1. Owner edits the .db locally (floor plan, menu, prices)
    2. Owner uploads to OCI bucket (same oci os object put as BIM OOTB)
    3. Waiter opens the bucket URL on their phone — full swipe mode
    4. Customer scans QR → same bucket URL with ?scope=table_7
    5. Edits (order taken, item marked served) write to local .db in browser
    6. Sync = waiter's browser re-uploads the modified .db to bucket (or a tiny cloud function merges kernel_ops logs — same merge pattern as git: each op has a timestamp and user_tag, conflicts are visible)

    This is not new infrastructure. It's the BIM share link pattern with write-back. The OCI bucket IS the cloud relay.

    7.4 Access Tiers (active in Step 2)¶

    ?mode= What it means Who uses it
    full All actions visible (create, edit, complete, void) Owner, manager
    operator Contextual actions only (take order, mark served) Waiter, picker, cook
    readonly View only + payment Customer, auditor, vendor
    request View + submit requests (needs approval) Customer self-order (Phase 2)
    ?scope= What it filters Example
    (empty) Full .db — all containers Owner view
    zone_patio One zone and its children Waiter's assigned section
    table_7 One container only Customer QR
    station_grill Kitchen station filter Cook's display

    In POC mode, these parameters are ignored — you see everything, you can do everything. They exist in the URL spec so that Step 2 is just adding ?scope= to a share link.

    7.5 Access Patterns by Domain (Step 2)¶

    Domain Full access Filtered access QR / public access
    BIM Project manager Discipline lead (scope=STR) Client walkthrough (readonly)
    WMS Warehouse manager Picker (scope=zone_A) Delivery driver (dock door)
    POS Store owner Section manager (scope=electronics) —
    F&B Restaurant owner Waiter (scope=zone_patio) Customer (scope=table_7)
    MFG Plant manager Line supervisor (scope=line_2) Auditor (readonly)
    Back Office CFO AP clerk (scope=payables) Vendor (their invoices only)

    8. Implementation Phases¶

    Phase 1 — The POC: Schema + Swipe + F&B on One Phone¶

    Goal: One person, one phone, one .db. Set up a restaurant, take orders, view as customer, settle bills. Proves the five-table schema, the swipe UX, the state machine, and the journal — all in one demo.

    Why F&B first (not BIM): The BIM viewer already exists and proves the 3D engine. The POC needs to prove the ERP layer — documents, state machine, journal. F&B is the most intuitive domain for that: everyone understands a restaurant. And the "customer sees their meal" moment is the viral hook.

    • [ ] Five tables in a restaurant.db (hand-crafted: 2 zones, 8 tables, menu items)
    • [ ] Doc status state machine in doc_engine.js (DRAFT→IN_PROGRESS→COMPLETED)
    • [ ] Journal auto-generation on COMPLETED (debit CASH, credit REVENUE)
    • [ ] Swipe card component (swipe.js) — gesture + card stack
    • [ ] All-in-one flow: owner view → waiter swipe → customer card → payment → journal
    • [ ] Heat map: table status overlay (red=waiting, green=served, grey=empty)
    • [ ] kernel_ops logs every transition (full audit trail from day 1)

    Phase 2 — BIM Domain Migration¶

    Goal: Rewire existing BIM viewer to use the same five tables. Proves that the F&B schema IS the BIM schema — no domain-specific tables.

    • [ ] Map existing extracted .db tables → containers + items
    • [ ] Construction order → documents + document_lines
    • [ ] 5D QTO → journal entries
    • [ ] Same swipe card for storey/room navigation (mobile BIM)

    Phase 3 — Cloud Relay (Step 2 activation)¶

    Goal: Upload .db to OCI bucket. Multiple devices access same data. ?scope= and ?mode= become live. This is the BIM share link pattern applied to all domains.

    • [ ] Upload/download .db to/from OCI bucket (reuse existing share flow)
    • [ ] ?scope= container filtering in viewer
    • [ ] ?mode= action button filtering
    • [ ] QR code generator (encodes bucket URL + scope + mode)
    • [ ] Write-back: modified .db re-uploaded or kernel_ops merge

    Phase 4 — WMS + Back Office + Remaining Domains¶

    9. Why This Wins¶

    9.1 Zero install¶

    Same promise as BIM OOTB. One HTML file. One .db file. One browser. No app store. No Docker. No server. Works on the $100 phone the warehouse picker carries, the waiter's Android, same as the architect's MacBook Pro.

    9.2 The TikTok effect¶

    ERP is the most boring software category in existence. Spatial + swipe makes it the most intuitive. The user never sees a form, a menu, or a 47-column table. They see their workplace and swipe through it.

    New users don't need training — they need 30 seconds. "This is your warehouse. Swipe through it. Tap the red ones." "This is your restaurant. Swipe through tables. Red means they're waiting."

    9.3 The QR code moment¶

    A customer scans a QR code and sees their meal in progress — no app, no login, no download. They watch the cook mark "plating" and know their food is coming. They tap "Pay" and leave. No card machine, no waiting.

    This is the demo that makes people say "I want this for my business." A warehouse picker seeing their pick path. A vendor seeing their invoice status. An auditor walking a factory floor. The QR code is the universal onramp — it turns anyone into a spatial ERP user in 2 seconds.

    9.4 Offline-first¶

    SQLite in the browser = works without internet. The warehouse picker downloads the .db at shift start, works offline all day, syncs at end. Construction sites with no connectivity. Ships. Mines. Remote factories. Restaurants with spotty WiFi. Anywhere iDempiere needs a server room, this needs a phone.

    9.5 The data model already exists¶

    iDempiere's 25-year-old ERP model (M_Product, C_Order, M_Locator, M_Movement) maps 1:1 to five SQLite tables. No invention. No abstraction mismatch. The compiler already proves this for construction — extending to WMS/POS/MFG/F&B is a catalog change, not an architecture change.

    9.6 Every user sees the same data, differently¶

    The restaurant proves the pattern: owner sees P&L heat map, manager sees table utilization, waiter sees their tables' order status, customer sees their meal, cook sees their station's queue. Five people, five views, same five tables, same .db file. The ?scope= and ?mode= parameters are the entire access control layer. No RBAC server. No user database.

    10. Mapping to iDempiere (Enterprise Ceiling)¶

    For organizations that outgrow the OOTB solo/team experience:

    OOTB table iDempiere table Migration path
    containers M_Locator + M_Warehouse Export containers → import as locators
    items M_Product + M_StorageOnHand Export items → import as products
    documents C_Order / M_InOut / M_Movement Export docs → import by doc_type
    document_lines C_OrderLine / M_InOutLine Lines follow their document
    journal GL_JournalLine Map 3 accounts → full chart of accounts

    The OOTB experience is the onramp. iDempiere is the highway. Users start with zero install. When they need multi-entity, compliance, full accounting — they graduate. The data migrates because the model is the same model.
