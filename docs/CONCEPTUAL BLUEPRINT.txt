### Layer Responsibilities

| Layer | Knows | Doesn't Know |
|-------|-------|--------------|
| **IFC** | Physical assembly | Intent, relationships |
| **YAML** | Semantic intent | Geometry, execution |
| **BOM** | Part relationships | Absolute positions |
| **Library** | Geometry + tack points | Assembly context |
| **ERP** | Orders + quantities | Design intent |
| **Compiler** | Constraints + math | Semantics, materials |

### The Golden Rule
```
Concrete data ONLY in YAML (bounds)
Geometry ONLY in Component Library (tack points)
Relationships ONLY in BOM (references)
Execution ONLY in ERP (orders)
Math ONLY in Compiler (constraints)
```

This keeps each layer pure, testable, and AI-friendly.

### Core Handler Patterns
```java
// System handler - pure container logic
SystemHandler {
    ALLOCATE hierarchy
    VALIDATE containment
    RESOLVE cross_discipline
    
    // No discipline names - just container types
}

// Penetration handler - relationship logic
PenetrationHandler {
    CHECK host_capacity
    VERIFY guest_clearance
    APPLY fire_rating
    ADD sleeve_if_needed
}

// Zone handler - spatial logic
ZoneHandler {
    DEFINE boundaries
    ASSIGN priority
    ENFORCE separation
    EXCEPT crossing_points
}

// Connection handler - tack point logic
ConnectionHandler {
    MATCH tack_points
    VERIFY orientation
    APPLY torque_spec
    TEST continuity
}

// Sequence handler - temporal logic
SequenceHandler {
    ORDER operations
    CHECK dependencies
    ALLOCATE temporary
    SCHEDULE inspections
}
```

// Spatial digest test
ASSERT final_positions

    .allMatch(p -> p.fits_in_parent())

    .stream()

    .stream()

## Blindspot Detection Prompt

```
Analyze current YAML/Java structure for:

1. MISSING RELATIONSHIPS
   - Are there connections between disciplines not captured?
   - Any cross-trade dependencies missing?
   - What about temporary vs permanent conditions?

2. INCOMPLETE CONSTRAINTS
   - Code requirements per region/locale?
   - Manufacturer-specific installation rules?
   - Warranty void conditions?

3. SEQUENCE GAPS
   - Testing before concealment?
   - Coordination between trades?
   - Phasing for occupied areas?

4. VALIDATION HOLES
   - What can't be verified mathematically?
   - Where does human inspection remain required?
   - Any as-built vs designed drift possible?

5. SCALABILITY CONCERNS
   - Large project performance?
   - Many disciplines interacting?
   - Complex geometry edge cases?
```

## Java Separation of Concerns - iDempiere Style

### Core Package Structure (AD Metadata Pattern)

```
com.bim.compiler
├── model/                 # POJOs - Pure data containers (like AD_Table)
│   ├── Container.java     # Holds children, bounds (like AD_Tree)
│   ├── Product.java       # Base attributes (like M_Product)
│   ├── AttributeSet.java  # Dynamic attributes (like M_AttributeSet)
│   └── TackPoint.java     # Connection points (like AD_Column)
│
├── engine/                # Stateless processors (like ModelValidator)
│   ├── Allocator.java     # CONTAINS logic - pure math
│   ├── Connector.java     # TACK_IO logic - pure relationships
│   ├── Validator.java     # CONSTRAINT checking - pure rules
│   └── Solver.java        # CONFLICT resolution - pure optimization
│
├── registry/              # Data access (like M_Product_BOM)
│   ├── BomRegistry.java   # Loads BOM structures (no geometry)
│   ├── LibraryRegistry.java # Loads geometry/tack points (no logic)
│   └── AttributeRegistry.java # Loads attribute sets (no context)
│
├── translate/             # YAML→Model mapping (like X_AD_Table)
│   ├── YamlParser.java    # Reads YAML (no business logic)
│   ├── IntentMapper.java  # Maps semantics to containers (no math)
│   └── ContextBinder.java # Binds to parent containers (no execution)
│
├── verify/                 # Integrity checks (like DocValidate)
│   ├── SpatialDigest.java # Hash of final positions (no generation)
│   ├── RosettaMatcher.java # Compare to original (no mutation)
│   └── DriftDetector.java # Catch hardcoding (no fixing)
│
└── execute/                # ERP integration (like M_InOut)
    ├── OrderGenerator.java # Creates work/purchase orders
    ├── BomExploder.java    # Flattens to ERP BOM format
    └── AttributeExporter.java # Pushes to iDempiere AD
```

### The "Translation-Separation" (Like AD_Field vs AD_Column)

public class IntentMapper {
    public Container mapToContainer(IntentModel intent) {
        // Turns "LIVING" zone into generic Container

        Container c = new Container();

    }

### The "Validator" Pattern (Like DocValidate)

```java
// verify/SpatialDigest.java - Pure hash (no interpretation)
public class SpatialDigest {
    public String compute(Container root) {
        // Recursively hash: bounds + children bounds
        // Returns deterministic string
        // If ANY position changes, hash changes
    }
}

// verify/RosettaMatcher.java - Compare only (no generation)
public class RosettaMatcher {
    public boolean matches(Container generated, String rosettaHash) {
        String currentHash = spatialDigest.compute(generated);
        return currentHash.equals(rosettaHash);
        // Never looks at WHAT the values are, just THAT they match
    }
}

// verify/DriftDetector.java - Catch cheating (no fixing)
public class DriftDetector {
    public List<Issue> detectHardcoding(Container c) {
        // Checks: are any positions absolute?
        // Or are all positions relative to parent?
        // Reports issues but doesn't fix them
    }
}
```

### Key Separation Rules

```
1. model/         →  Only data structures (like POJOs)
2. engine/        →  Only stateless logic (like services)
3. registry/      →  Only data access (like DAOs)
4. translate/     →  Only YAML→model mapping (like parsers)
5. verify/        →  Only validation (like checkers)
6. execute/       →  Only ERP integration (like adapters)

NO CROSS-LAYER DEPENDENCIES:
- engine never calls registry (data passed in)
- model never has logic (pure POJOs)
- translate never does math (just mapping)
- verify never modifies (just reports)
- execute never knows about YAML (just resolved containers)
```

This mirrors iDempiere's AD_Table (model), AD_Process (engine), M_Product (registry), DocValidate (verify) separation - each layer has one job and does it purely.
