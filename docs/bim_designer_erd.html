Self-contained output: work_output.db carries YAML, Order, and ASI definitions inside it during init. Backend tools (SQL reports, admin dashboards) can read the design without Blender. The DB filename is user-configurable (default: work1.db), noted in the YAML or Order profile.
Design Session Data Flow: The user works in Blender (visual BBox or ORDER View). All edits modify C_OrderLine + M_ASI in the design layer. The BOM templates are read-only references. Three tiers of change exist — only structural changes might eventually need a Promote.
—— Change Tiers ——

Parameter Change

Resize room: 4000 → 4500mm
Change material: Brick → Concrete
Writes: ASI only
BOM touched: No
Cost: Cheap, frequent

Positional Change

Move room 500mm along X
Reorder rooms in storey
Writes: dx/dy/dz on OrderLine
BOM touched: No
Cost: Cheap

Structural Change

Add/remove room
Add storey, change room type
Writes: OrderLine add/delete
BOM touched: No (until Promote)
Cost: Medium

Blender mechanisms: GPU batch rendering via UNIFORM_COLOR shader (no mesh objects). Lazy sync timer at 200ms via bpy.app.timers detects scene property changes for ORDER View ↔ BBox sync. Undo via scene["_design_bboxes"] custom property (Blender's undo stack tracks scene props automatically).

—— Promote Metadata (Birth Certificate) ——

PromoteRequest

buildingId
owner — who approved
complianceRef — UBBL 2012 s33
provenance — GENERATIVE | ADAPTED

PromoteResponse

success
buildingId
bomEntriesCreated
dangles[] — unresolved refs
error

Dangles Check

Blocked if unresolved child refs:
  ROOM_KT → WINDOW_CUSTOM ✘
  ROOM_BD → DOOR_SLIDING ✘
  FLOOR_GF → all resolved ✔
Never pass NULL forward
Promote is rare and deliberate — the iDempiere equivalent of Document Process → Complete. Saves are cheap (many variants in work_output.db). Promote creates permanent BOM entries in the curated catalog. The BOM stays clean: only proven, validated, owner-signed designs enter. Dangles are blocked, not silently passed.
Architecture: Thin Python addon (Blender) ↔ TCP ndjson ↔ Java DesignerServer. Like iDempiere's ZK Ajax UI: server produces the data model, client renders it as UI components. The Python side sends events, the Java side returns data. No BIM logic in Python.
