Self-contained output: work_output.db carries YAML, Order, and ASI definitions inside it during init. Backend tools (SQL reports, admin dashboards) can read the design without Blender. The DB filename is user-configurable (default: work1.db), noted in the YAML or Order profile.
Design Session Data Flow: The user works in Blender (visual BBox or ORDER View). All edits modify C_OrderLine + M_ASI in the design layer. The BOM templates are read-only references. Three tiers of change exist — only structural changes might eventually need a Promote.
—— Change Tiers ——

Parameter Change

Resize room: 4000 → 4500mm
Change material: Brick → Concrete
Writes: ASI only
BOM touched: No
Cost: Cheap, frequent

Positional Change

Move room 500mm along X
Reorder rooms in storey
Writes: dx/dy/dz on OrderLine
BOM touched: No
Cost: Cheap

Structural Change

Add/remove room
Add storey, change room type
Writes: OrderLine add/delete
BOM touched: No (until Promote)
Cost: Medium

Dangles Check

Blocked if unresolved child refs:
  ROOM_KT → WINDOW_CUSTOM ✘
  ROOM_BD → DOOR_SLIDING ✘
  FLOOR_GF → all resolved ✔
Never pass NULL forward
Promote is rare and deliberate — the iDempiere equivalent of Document Process → Complete. Saves are cheap (many variants in work_output.db). Promote creates permanent BOM entries in the curated catalog. The BOM stays clean: only proven, validated, owner-signed designs enter. Dangles are blocked, not silently passed.
Architecture: Thin Python addon (Blender) ↔ TCP ndjson ↔ Java DesignerServer. Like iDempiere's ZK Ajax UI: server produces the data model, client renders it as UI components. The Python side sends events, the Java side returns data. No BIM logic in Python.

WF-BB §26 — Wireframe-First Interaction Protocol: BBox is the interaction mode. Full geometry is the settled state. Three rules: (1) First load = bbox wireframe, (2) Edit existing = per-object BOUNDS + focused SOLID + bbox overlay, (3) Add new = bbox for new item, BOUNDS for rest.
—— Phase Detection ——

Phase 1 — No Geometry

Trigger: createNew, addRoom, addStorey
Visual: All GPU overlay bboxes
Category colours (DESIGN_COLORS)
Focus: vivid bbox, rest grey
Exit: CO → Compile to 3D

Phase 2 — Full Geometry

Trigger: Toggle Design with mesh objects
Visual: All objects → display_type='BOUNDS'
Focused: SOLID + show_in_front + vivid bbox
Orientation markers: RGB axes (R=+X, G=+Y, B=+Z)
Exit: Toggle Real → restore original display

Auto-Detect

has_full_geometry()
Checks: any MESH with bim_designer_loaded tag
True → Phase 2
False → Phase 1
Zero user action needed
—— Phase 2: Per-Object Display Control ——

Unselected Object

display_type = 'BOUNDS'
display_bounds_type = 'BOX'
color = (0.4, 0.4, 0.4, 0.3)
Native Blender bbox — grey, spatial context
Original display stored in _wf_original_display

Focused Object

display_type = 'SOLID'
show_in_front = True
+ GPU vivid bbox overlay (thick lines, category colour)
+ RGB orientation arrows at bbox centre
Full geometric detail visible

New Item (Rule 3)

GPU overlay bbox (Phase 1 style)
Category colour, thin lines
No SOLID geometry yet
Visually distinct from BOUNDS objects
On CO → compiles to mesh → joins BOUNDS pool
