Two Apps. One Kernel.

Their code: 76% bloat, 14% code logic — both the ERP and BIM legacies. Ours: one shared kernel (4%) plus the ERP (3%) and BIM (3%) logic that runs on it — 10% total, even at full logic parity.
Bloat 1,228,468 LOC — DB/ORM, JVM/OSGi/servlets/JDBC, ZK UI, tests/batch Code logic — both legacies (iDempiere + Bonsai); iDempiere's share measures 198,679 LOC Kernel — SQLite‑WASM + Three.js + signed oplog (shared by both apps) ERP logic — iDempiere rules ported into the kernel BIM logic — Bonsai/IFC rules ported into the kernel

iDempiere: 1,427,147 Java LOC / 4,465 files (2026-06-08). Bonsai (CAD, Python): 235,365 LOC — measured. For scale, a full desktop CAD app is bigger still: FreeCAD (C++/Python): 1,917,224 LOC / 5,413 files, measured 2026-08-07 via github.com/FreeCAD/FreeCAD. (Navisworks: proprietary, no public LOC — not included, not guessed.)

The 76/14 legacy split and the 4/3/3 kernel split are a round, conservative big-picture estimate, not a line-by-line measurement. Basis: bloat 1,228,468 + logic 198,679 (both measured) against a projected ≈150,000–160,000 LOC kernel — today's engine (55,283 measured 2026-08-07, plus growth headroom) roughly doubling for full AD-interpretation breadth, plus 100% of the remaining business logic at a conservative 3× fold (104,940 M-class code-LOC ÷ 3 ≈ 35,000, below the documented 5–8× range on purpose) — split across the shared kernel and the two domains' logic. Even at that full-parity basis: ~10× fewer lines than iDempiere alone. Exact snapshot + full method in the write-up.
