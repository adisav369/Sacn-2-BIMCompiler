SQLite-in-Browser Architecture — bim-ootb ACTUAL

Verified against the deployed viewer/modeller/erp code, 2026-07-04
Corrects Screenshots/SQLiteProjectMap.png — that chart's generic sqlite3-wasm layers (VFS/threading/API) are accurate documentation for the official sqlite3-wasm API, but its "BIMCompiler notes" callout describes an architecture this project does not use. 6 of 7 project-specific claims there are false or unbuilt.
LAYER 1 — APPLICATION CODE (actual)
sql.js Database API
new SQL.Database(bytes)
db.exec(sql) / db.prepare(sql)
This is the sql.js port (older Emscripten build), NOT the official sqlite3.wasm OO1/capi/Promiser API the source chart depicts. No sqlite3InitModule, no oo1 namespace, no Promiser anywhere in either repo.
better-sqlite3 (native)
Database(path) — Node only
Used only in bim-compiler's offline extraction/QTO/build scripts (e.g. mep_qto_populate.js, wizard_storeys.js). Never loaded in the browser.

LAYER 2 — WASM MODULE (actual)
Standard build
lib/sql-wasm.js + .wasm
Loaded main-thread via fetch('lib/sql-wasm.wasm') (viewer/loader.js:6), with a jsDelivr CDN fallback if the local file 404s.
FTS5 build (swapped in)
lib/sql-wasm-fts5.js + .wasm
Stock sql.js has no FTS5. erp/erp.html / erp/genesis.html load the special FTS5-compiled build instead. This is the one claim from the original chart that holds.
↓
LAYER 3 — PERSISTENCE (actual — there is no VFS choice)
Whole-file fetch → whole-file in-memory DB. No OPFS-SAH, no kvvfs, no IndexedDB-backed VFS.
fetch(url).then(r=>r.arrayBuffer()).then(b=>new SQL.Database(new Uint8Array(b)))
viewer/streaming.js:1442,1502,1516,1580 — every .db file (meta.db, geo.db, extracted.db, component_library.db, ad_seed.db…) is downloaded complete over HTTP, then held entirely in the JS heap for the session. Memory scales with total building size, not with what's on screen.
Dead code found: viewer/lib/httpvfs.js (a real byte-range-fetch Worker VFS) is loaded on some pages, and streaming.js has guarded branches for it (A._useRangeStream && A._rangeDb, lines 54/387/520/544). But _rangeDb and _useRangeStream are never assigned anywhere in either repo — the branch is unreachable, every load falls through to the full-fetch path above. (This also corrects this project's own memory note "viewer STREAMS via httpvfs" — the smooth large-building load is DLOD render-culling, see Layer 4, not byte-range DB streaming.)
erp/vfs_detect.js:42-47 only probes OPFS capability for a possible future switch; erp/idempiere.html:828 says outright OPFS persistence is "not yet" wired and blocked on GH-Pages hosting anyway.
↓
LAYER 4 — THREADING (actual)
Main thread only. Every SQLite call is synchronous JS on the UI thread.
No Worker ever runs sql.js. What actually keeps large buildings (e.g. Terminal, 125K elements, ~12s smooth) usable is DLOD — a Three.js frustum/visibility culling + bbox-batching layer over the render loop (viewer/streaming.js §S261/§S262/§S265) — it reduces draw calls per frame, it does not reduce what's resident in the SQLite heap. A future building large enough to blow the JS heap on load would still stall even though frames stay smooth once loaded — DLOD masks the render cost, not the load cost.
↓
LAYER 5 — API PATTERNS (actual)
Geometry hot loop
.exec() dominant
11 .exec() call sites vs 4 .prepare() in viewer/streaming.js — not prepared-statement-driven in the browser. .prepare()/.get()/.run() reuse exists only in the Node-side better-sqlite3 build tooling, a separate binding entirely.
Not used anywhere
rowMode · json_each() · sqlite3Worker1Promiser
Zero matches across both repos for all three. They're official sqlite3-wasm concepts the original chart's callout borrowed — this codebase doesn't have the API surface to use them.
