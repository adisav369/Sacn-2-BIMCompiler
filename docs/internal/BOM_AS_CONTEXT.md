# BOM-as-Context — Grid Lines Carry BOM Rules

> **One-line:** Every grid line carries a BOM rule set. When the grid moves, child elements recompute quantities and positions like a manufacturing assembly line.

**Status:** Concept — needs deeper design session
**Builds on:** [BOMBasedCompilation.md](BOMBasedCompilation.md) §2 (compilation model), §6 (verbs)
**Applies to:** [RED_PILL.md](RED_PILL.md) (browser-side forward path), [REFACTOR_DOC_CANVAS.md](REFACTOR_DOC_CANVAS.md) (grid_state + grid_recompose)

---

## 1. The Insight

The BOM is already a recipe: parent → children with quantities and spatial offsets. The verbs (TILE, FRAME, ROUTE) already expand recipes into placements using spacing rules.

The missing link: **the grid line IS the BOM parent's spatial anchor.** When a grid line moves, the BOM rule set attached to it recomputes its children — not just translating them, but recounting, re-spacing, and re-laying them out. This is what manufacturing does: change the assembly jig dimension, and the assembly reconfigures.

This is not a new concept bolted onto the compiler. It is the original BOM concept applied to the browser's grid-drag interaction. The Java pipeline does `BOM → verb → placement`. The browser should do `grid drag → BOM rule → re-placement`.

---

## 2. What a Grid Line Carries

A grid line is not just a position. It is a **context** for its attached BOM set:

| Property | What It Means | Example |
|---|---|---|
| `spacing` | Distance between repeated children | Windows at 1800mm centers |
| `edgeOffset` | Margin from grid line to first/last child | 600mm from wall corner to first window |
| `fixedCount` | Elements that don't change count (doors) | 1 main door per wall segment |
| `fillRule` | How remaining space is distributed | `uniform` (equal spacing), `packed` (minimum gap), `centered` |

These are not new parameters — they are the same values the Java TILE/FRAME/ROUTE verbs already use. The browser extracts them from the reference building's placement pattern, and re-applies them when the grid moves.

---

## 3. What Happens on Grid Drag

**Current behavior (S270):** Elements translate or scale. Quantity is fixed. A wall with 4 windows stays 4 windows even if the wall stretches from 8m to 14m.

**BOM-as-Context behavior:** The wall's BOM rule says `spacing=1800, edgeOffset=600`. At 8m: `(8000 - 2×600) / 1800 = 3.8 → 4 windows`. At 14m: `(14000 - 2×600) / 1800 = 7.1 → 7 windows`. Three new windows materialize. Their positions are computed, not placed manually.

This is exactly what the TILE verb does at compile time. BOM-as-Context runs it at drag time.

---

## 4. Individual Overrides and Promotion

**Override:** User manually moves one window. That element gets an `overrideFromBom` flag. Subsequent grid drags re-layout all windows EXCEPT the overridden one. It stays where the user put it.

**Promotion:** After overriding, the system can offer: "You changed this window to 1600mm spacing. Apply to all windows on this wall?" If accepted, a new BOM variant is created (`spacing=1600`) and the override flag is cleared — the element is now part of the new rule, not an exception.

This mirrors manufacturing: a one-off modification to a jig becomes a new jig variant once validated.

---

## 5. Sub-Layer BOMs — Recursive Context

A grid line's BOM set can contain children that are themselves BOM sets:

- **Hall → dining set:** Drag hall wall → re-space dining tables (buffer spacing between sets)
- **Wall → windows + 1 fixed door:** Drag grid → windows recount, door stays (fixedCount=1)
- **Floor → rooms → furniture:** Floor grid changes → rooms resize → furniture re-layouts

Each level is atomic. The hall doesn't know about chair spacing — it knows about table spacing. The table BOM knows about chairs. This is the recursive BOM principle from BBC.md §2, applied to live editing.

---

## 6. Copy, Transpose, Factor

| Operation | What It Does |
|---|---|
| **Copy** | Apply wall A's BOM rules to wall B (same window spacing, same door count) |
| **Transpose** | Apply X-axis wall rules to Z-axis wall (rotate the BOM set 90°) |
| **Factor** | Extract common rules across walls into a shared BOM template (like `extractBOMAbstractSets` in the Java pipeline) |

These operations exist conceptually in the Java compiler (abstract sets, product categories, substitution). BOM-as-Context makes them interactive.

---

## 7. Why This Is Novel

Existing BIM tools are **object-centric** — each window is edited individually (Revit) or generated by a visual script (Grasshopper). Both require explicit parameter definition before design begins.

BOM-as-Context is **grid-centric** and **rule-driven**:
- Rules are **extracted** from the reference building, not authored
- Rules are **implicit** in the placement pattern (spacing, offset, count)
- Rules are **editable** by dragging grid lines, not by scripting
- Rules are **promotable** from one-off overrides to reusable variants

This is the construction remodeling workflow: you start with a static IFC, extract its spatial grammar, and "parametrize" it after the fact — without ever touching a parametric modeller.

---

## 8. What Already Works — Don't Lose This

The S270 grid kinematics engine already achieves clean wall-pulling:

- **ATTACH:** Wall centerline near grid → rigid translate (wall slides with grid)
- **SPAN:** Grid inside wall body → scale (wall stretches)
- **EDGE:** Grid at wall edge → stretch or translate depending on direction
- **Bay-proportional:** Interior elements (furniture, doors) redistribute proportionally

This was proven working before the grid flood and phantom delta bugs broke it. Those bugs are now fixed (label-based tracking, door/window grid suppression). The clean wall-pull behavior — walls move without gaps, spanning elements stretch, interior elements redistribute — is the **baseline that BOM-as-Context extends**, not replaces.

BOM-as-Context adds a layer on top: after the geometry moves (TRANSLATE/SCALE), the BOM rules recount children (windows, fixtures) for the new bay width. The geometry layer stays. The recount layer is additive.

**Key:** The 98-test engine (`grid_kinematics.js`) and the 8 relation types are preserved. `RELAYOUT` would be a 9th command type that fires after TRANSLATE/SCALE, not instead of them.

---

## 9. Deeper Impact When Done Right

If this works, the BOM-as-Context framework changes what the product IS:

- **Today:** The product is a BIM viewer with grid drag (translate/scale geometry)
- **With BOM-as-Context:** The product is a **manufacturing-grade recomposition engine** — grid drag triggers BOM re-expansion, quantity recount, spacing recompute, and layout regeneration

This is the difference between moving furniture around a room (what every BIM tool does) and changing the room's assembly jig so the furniture reconfigures itself (what manufacturing does). The BOM is the jig. The grid is the jig's adjustment handle.

The 21 buildings already verified through Rosetta Stone gates prove the BOM extraction works. BOM-as-Context is the forward path: extract → modify → re-expand → verify. Same pipeline, browser-side, interactive.

## 10. Open Questions (Next Session)

These need deeper discussion with the user before implementation:

1. **Extraction accuracy:** How reliably can spacing/edgeOffset/fixedCount be extracted from arbitrary IFC files? The TILE/FRAME/ROUTE verbs already detect patterns — is that sufficient or do we need user confirmation?

2. **Rule conflict resolution:** When two grid lines both claim the same element, which BOM rule wins? The engine currently assigns each element to its "best" grid — does BOM-as-Context change that?

3. **Quantity change rendering:** Adding 3 windows to a stretched wall requires new geometry. Where does it come from — clone from existing window? Lookup from product catalog? This is the materialization problem.

4. **Override scope:** Does an override apply to one instance, one wall, one storey, or the whole building? The BOM hierarchy suggests per-BOM-level, but the UX needs to be intuitive.

5. **Verb re-use:** The Java TILE verb has parameters (grid dimensions, step size). Can the browser re-use these parameters directly, or does it need a simplified version?

6. **Relationship to the existing `grid_kinematics.js` engine:** The engine currently returns TRANSLATE/SCALE/ROOF_VERTICES commands. BOM-as-Context would add a new command type: `RECOUNT` or `RELAYOUT`. How does this integrate?
