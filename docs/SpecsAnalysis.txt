SpecsAnalysis — M_Product_Category + AD_Org Reconciliation
============================================================
Date: 2026-03-25
Sources: DISC_VALIDATION_DB_SRS.md §10-11, DATA_MODEL.md §2+§7,
         BIM_Designer_SRS.md §30.7, DISC_VALIDATE_SRS.md §3-4,
         MANIFESTO.md §Category Population, TerminalAnalysis.md §M_Product_Category

1. TWO ORTHOGONAL AXES (confirmed)
-----------------------------------
  AD_Org             = WHO owns (discipline: ARC, STR, FP, ELEC, ACMV, CW, SP, LPG, REB, * shared)
  M_Product_Category = WHAT type (taxonomy: sprinkler head, pipe segment, wall)

  Link: M_Product_Category.AD_Org_ID → AD_Org (each category knows its owning discipline)
  Source: DISC_VALIDATION_DB_SRS.md line 471-473, 794-798

2. AD_Org FOR HIERARCHY (confirmed — iDempiere native)
-------------------------------------------------------
  iDempiere's AD_Org supports hierarchy natively via IsSummary flag + AD_OrgInfo.
  A parent "MEP" org can summarize FP+ELEC+ACMV+CW+SP+LPG as peers.
  RE structural frame → AD_Org = '*' (shared); RE furniture/finishes → AD_Org = 'ARC'.
  AD_Org table already spec'd with IsSummary (DISC_VALIDATION_DB_SRS.md line 726).
  No parent MEP row seeded yet — to be added when hierarchy is implemented.

3. Parent_Category_ID — UNNECESSARY, TO BE DROPPED
----------------------------------------------------
  Standard iDempiere M_Product_Category is FLAT (no parent FK).
  BIM_Designer_SRS.md §30.7.1 added Parent_Category_ID as a custom self-reference.
  DECISION (2026-03-25): DROP Parent_Category_ID. Reasons:
  - iDempiere M_Product_Category is flat. That is the religion.
  - The cascade (RE→GF→LIVING→leaf) is already expressed by M_BOM_Line parent-child.
  - Swap-pool constraint = match m_product_category_id at the same BOM level.
  - AD_Org.IsSummary handles discipline grouping (MEP→FP+ELEC+...) natively.
  - Parent_Category_ID duplicates the BOM tree at the category level.
  Migration: DATA_MODEL.md §7.6 session N+8 — drop column.

4. M_Product_Category COLUMNS (iDempiere standard)
----------------------------------------------------
  Required: M_Product_Category_ID, Name, Value, IsActive
  Project addition: AD_Org_ID (FK to AD_Org)
  Questionable: Parent_Category_ID (see §3 above — may drop in favour of AD_Org hierarchy)
  Gap: DATA_MODEL.md §2 omits Parent_Category_ID from schema. If kept, must be added.

5. bom_category → AD_Org REPLACEMENT (confirmed)
--------------------------------------------------
  "bom_category is a string proxy for AD_Org" — DISC_VALIDATION_DB_SRS.md line 789-792.
  Once AD_Org_ID exists on m_bom, bom_category becomes derived display or drops entirely.
  Migration table: DISC_VALIDATION_DB_SRS.md §11.6.3 (8 table.column replacements).

6. DocBaseType — REDUNDANT (confirmed)
----------------------------------------
  DocBaseType = singular 'Construction'. Classification lives on M_Product_Category,
  not on C_DocType. Legacy columns (DocBaseType, DocSubType) deprecated per DATA_MODEL.md §7.
  Migration: remove after M_Product_Category fully adopted on all BOM databases.

7. ProductCategory.java vs M_Product_Category TABLE
-----------------------------------------------------
  ProductCategory.java = Java class with deriveDiscipline(ifcClass) — LEGACY inference.
  M_Product_Category   = database table — DATA-DRIVEN taxonomy.
  They are related but different. The Java class is marked for retirement when AD_Org
  is implemented (DISC_VALIDATION_DB_SRS.md line 774-786). Post-AD_Org, deriveDiscipline()
  becomes extraction-only fallback, never called in the compile path.

8. TE (Terminal) CLASSIFICATION — RESOLVED
--------------------------------------------
  TE is M_Product_Category = CO (Commercial), with discipline-driven L2 cascade
  (ARC, STR, FP, ACMV, ELEC, CW, SP, LPG). Confirmed by TerminalAnalysis.md line 39.
  MANIFESTO.md updated 2026-03-25 to move TE from "(unclassified)" to CO.
