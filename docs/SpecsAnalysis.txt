--------------------------------------------------

  - M_InOut = delivery batch (truck arrives with wall panels)
  - M_InOutLine = individual material receipt (100 panels received)
  - M_InOutLineMA = lot/attribute tracking (batch number, inspection date)

  **Action:** Correct SystemContract.md §6 M_InOut mapping. Move to 4D
  scheduling context under ProjectOrderBlueprint.md §5.1. Plot placement

  See also: ProjectOrderBlueprint.md §5.1 (4D = topological sort of BOM tree).
  M_InOut adds the physical logistics dimension — when materials actually

14. AD_Val_Rule — TWO TYPES OF RULES (spatial + regulatory) — DONE (S79: DocValidate §0 written, prompt 15)
-------------------------------------------------------------
  Rules come from two sources that are SYMBIOTIC, not competing:

  a. SPATIAL (mined from buildings):
     Placement rules learned from real extracted buildings. Dimensions per
     (ifc_class × storey). These encode "what buildings actually look like" —
     empirical patterns from 35 real buildings. Stored in ad_space_type,
     ad_element_mep, ad_space_dim, placement_rules tables.
     → Already documented in DISC_VALIDATION_DB_SRS.md §10-11.

  b. REGULATORY (from standards bodies):
     Building codes: UBBL (Malaysia), NFPA 13 (fire), IBC (US), BCA (Australia).
     These encode "what the law requires" — sprinkler spacing, fire door
     frequency, emergency light proximity to exits.
     → Stored in ad_val_rule with jurisdiction scope (pack_id, valid_from/to).
     → Partially documented in DocValidate.md, ad_code_requirement table.

  The two are SYMBIOTIC:
  - Spatial rules say: "rooms of this type typically have 1 sprinkler."
  - Regulatory rules say: "NFPA 13 requires sprinkler coverage ≥ 3000mm."
  - Together: spatial rules propose placement, regulatory rules validate it.
  - Compiler places per spatial rules, AD_Val_Rule gates per regulatory rules.
  - This IS the Three Concerns: spatial = WHERE, regulatory = HOW.

  **Action:** This is a CROWD PULLER for the github.io site. Create a
  dedicated spec (or major section in DocValidate.md) documenting:
  - The two rule sources and their symbiotic relationship
  - How spatial rules are mined (extraction pipeline → ad_space_type/dim)
  - How regulatory rules are authored (standards → ad_val_rule + pack_id)
  - How they compose at compile time (spatial proposes, regulatory validates)
  - Rule provenance: every rule traces to either a building (extraction)
    or a standards clause (authority_id + clause_ref on ad_val_rule)
  - Cross-links from MANIFESTO §HOW, DocValidate.md, DISC_VALIDATION_DB_SRS.md
  - Prominent link from github.io landing page (INDEX.md)

  **Prompt task:** Write prompts/15_rule_provenance_spec.md for this. — DONE (9f1212f)

  power the Process Engine for interactive ERP. The BIM compiler uses
  custom processIt() dispatch because it's a batch compiler, not an
  interactive system — there's no UI event loop driving ModelValidator.

  Owner confirms: this is CORRECT for current scope. Wire ModelValidator
  pattern later when the system scales to enterprise (multi-user, real-time
  validation, interactive BOM editing in the designer).

  **Note for enterprise scaling:**
  - ModelValidator alignment becomes necessary when BIM Designer supports
    real-time collaborative editing (multi-user, conflict detection)
  - At that scale, also relevant: Federated Model Spatial DB addon
    (93% memory reduction on 93K elements — StrategicIndustryPositioning.md
    line 238). The current in-memory approach handles TE's 48K elements but
    won't scale to multi-building federation without spatial DB partitioning.
  - These two (ModelValidator + FederatedModel) are companion features for
    enterprise deployment, not needed for the current compiler pipeline.

  **Action:** Add note to ProjectOrderBlueprint.md §14 (roadmap) under
  "Enterprise Scaling" heading.

PART 4 — TRIM Verb + Roof Swap Gap Analysis (2026-03-26)
============================================================
Investigating whether TRIM WALLS TO ROOF fires in the SH and DM
compiler flows, and whether OrderLine replace (roof swap) is spec'd.

20. SH ROOF IS CURVED — DSL SAYS FLAT (MISMATCH)
----------------------------------------------------
  dsl_sh.bim declares `ROOF pitch:0deg overhang:600mm` (flat).
  IFC source: `Roof_Flat-4Felt-150Ins-50Scr-150Conc-12Plr` (.NOTDEFINED.).
  ACTUAL: component_library.db product LOD is a curved roof mesh.
  The library geometry is the truth — the DSL pitch:0deg is wrong or
  irrelevant since the mesh itself defines the shape.

  **Gap:** TrimWallsToRoofVerb tent model only handles FLAT and PITCHED
  (linear slope). A curved roof needs a different surface estimation
  (e.g. arc interpolation from AABB, or sample Z from mesh vertices).
  Current verb would treat the curved roof AABB as auto-detect pitched
  (tent model fallback), which is an approximation, not correct for curves.

  **Action:** Either (a) add curved-roof surface model to TrimWallsToRoofVerb,
  or (b) accept tent-model approximation and document the limitation.

  **Decision (S81):** Accept tent-model approximation for now. SH's curved
  roof is an edge case — the tent model uses the AABB peak as ridge height,
  which gives a reasonable wall trim. Document limitation in BIM_COBOL.md
  §TRIM verb section. Curved-roof surface model deferred to Phase F.

23. DSL (.bim) REDUNDANCY WITH YAML
--------------------------------------
  classify_sh.yaml serves as C_Order/C_OrderLine stand-in (product,
  BOM IDs, rooms, AABB, origin). dsl_sh.bim defines GRID, STOREY,
  ROOF, room bounds, and element placement (WINDOW, DOOR directives).

  Current split:
    YAML = WHAT (order: which building, which rooms, BOM references)
    DSL  = WHERE (grid spacing, storey heights, room bounds, openings)

  These overlap: YAML has aabb_mm + origin_m per room (WHERE data),
  while DSL has GRID+bounds (also WHERE data). For generative buildings
  (DM), YAML alone has all the data — dsl_dm.bim adds nothing beyond
  room names that YAML already declares.

  **Question for ActionRoadmap review:** Can DSL be retired in favour
  of enriched YAML? Or does DSL serve a role that YAML cannot (e.g.
  GRID axis algebra, parametric room bounds, WINDOW/DOOR directives)?
  For extracted buildings (SH, FK), the DSL captures IFC-derived layout
  that YAML doesn't replicate. For generative buildings (DM), DSL is
  redundant. Decision needed: converge on one format or keep both with
  clear roles.

  **Decision (S81):** Keep both with clear roles for now.
  - YAML = WHAT (C_Order stand-in: products, BOMs, room assignment)
  - DSL = WHERE for extracted buildings (grid algebra, storey heights,
    WINDOW/DOOR directives that YAML cannot express)
  - Generative buildings: DSL is generated from YAML (already the case
    for DM). DSL retirement deferred — GRID axis algebra has no YAML
    equivalent yet. Add to ACTION_ROADMAP.md as Phase G (Format Convergence).
