1. SYSTEM CONFIGURATION (ad_sysconfig)
=====================================================================

The compiler's runtime behaviour is governed by config rows, not code:

  config_key          | config_value        | Effect
  --------------------|---------------------|----------------------------
  placement_mode      | RELATIONAL          | Use ad_element_rule (not flat)
  closest_fit         | true                | Library mesh closest match
  exclude_ifc_class   | IfcOpeningElement    | Skip opening voids in output

Toggle placement mode without code change:
  UPDATE ad_sysconfig SET config_value='FLAT'
  WHERE config_key='placement_mode';

6. TRANSPARENCY PIPELINE (Data → Viewer)
=====================================================================

Transparency is 100% data-driven. The chain:

  ad_element_rule.material_name  (e.g., 'Window_W1')
         ↓ [Java: RelationalResolver]
  PlacementAD.Placement.materialName()
         ↓ [Java: BuildingWriter]
  output DB: elements_meta.material_name
         ↓ [SQL: LEFT JOIN]
  output DB: surface_styles.transparency  (e.g., 0.6)
         ↓ [Python: Bonsai Federation addon]
  Blender: blend_method = 'BLEND', Alpha = 0.4

  Transparent styles in surface_styles:
    Glass            | transparency = 0.9 | SH/DX windows + curtain panels
    Glass - Clear    | transparency = 0.64| Tinted glass
    Window_W1        | transparency = 0.6 | TB-LKTN standard windows
    Window_W2        | transparency = 0.6 | TB-LKTN secondary windows
    Window_W3_Small  | transparency = 0.6 | TB-LKTN wet room windows
    Shower           | transparency = 0.3 | Shower screens
    Interior Fill    | transparency = 0.85| Interior transparent fills

  TRAP: IFC exports assign material_name = 'Window Frame' to IfcWindow
  elements (the frame, not the glass). Migration RM6 fixes this to
  'Glass' in both ad_element_placement and ad_element_rule.

8. RELATIONAL vs FLAT — SAME BUILDING, TWO MODES
=====================================================================

The compiler can compile SH and DX from either mode:

  FLAT (ad_element_placement):
    - 55 rows for SH, 1085 for DX, 51088 for Terminal
    - Pre-computed world coordinates (minX, maxX, minY, maxY, minZ, maxZ)
    - Extracted from IFC reference files
    - Serves as TEST ORACLE: computed coordinates must match within 0.001mm

  RELATIONAL (ad_element_rule):
    - 55 rules for SH, 1085 for DX, 58 for TB-LKTN
    - Rules reference grid + room + wall + fraction/boundary positions
    - Coordinates COMPUTED at runtime by RelationalResolver
    - Shadow validation: 100% match for SH and DX (0.001mm max error)

  Toggle: UPDATE ad_sysconfig SET config_value='FLAT'
          WHERE config_key='placement_mode';

  TB-LKTN has NO flat placement data — it can ONLY compile in
  RELATIONAL mode. This is the proof that the system is generative.

These are places where the data layer is incomplete, causing the

  -----------------------------|---------------------------|------------------
  TB-LKTN wall types missing   | 100mm depth for all       | Add to ad_wall_type
  TB-LKTN door rotation        | NS doors face wrong way   | Orientation in rule

  TB-LKTN kitchen sparse       | Minimal fixtures          | Add BOM rules
  TB-LKTN furniture position   | Center-of-room approx     | Refine fractions

  SH roof-glass intersection   | Glass through curved roof | Clipping rule needed

10. AUDIT CONCLUSION
=====================================================================

ZERO HARDCODED VALUES IN JAVA FOR BUILDING-SPECIFIC DATA.

Every element's position, dimensions, material, and transparency is
driven by one of these tables:

  Table                | What it drives           | Rows
  ---------------------|--------------------------|------
  ad_sysconfig   | Runtime mode switches    | 3
  ad_building_grid     | Grid coordinates         | ~70
  ad_room_boundary     | Room extents             | ~50
  ad_wall_face         | Wall types + adjacency   | ~120
  ad_element_rule      | Element placement rules  | 1,198
  ad_element_placement | Flat placement (Oracle)  | 68,472
  ad_wall_type         | Wall thicknesses         | 15
  ad_geometry_map      | Element→mesh mapping     | ~200
  surface_styles       | Material PBR properties  | 80
  m_bom               | Furniture assembly rules | 22
  m_bom_line         | Assembly components      | 82
  m_attribute   | Spatial offsets           | 214

The compiler Java code is a RESOLVER — it reads these tables and
computes geometry. It does not contain building-specific values.

Where output looks wrong (opening depth, door rotation, sparse
furniture), the fix is ALWAYS a data update — never a code change.
