## Context

§6.3 declares a three-stage validation model:
- **Stage 1 (DocEvent per Org):** blanket discipline rules + government standards (NFPA 13, UBBL)
- **Stage 2 (AttributeSet):** per-product/per-instance resolution
- **Stage 3 (AD_Val_Rule):** user override on specific lines

The claim is that validation logic lives in metadata (ERP.db), not hardcoded in Java.
This is true for structural dimension rules (415 ad_val_rule rows mined from output DBs).
It is NOT yet verified for MEP.

## Audit — run these queries, report findings

### Q1: What AD_DocEvent_Rule rows exist?

```sql
SELECT r.rule_id, r.rule_name, r.AD_Org_ID, r.trigger_event,
       COUNT(p.param_id) params
FROM AD_DocEvent_Rule r
LEFT JOIN AD_DocEvent_Rule_Param p ON r.rule_id = p.rule_id
GROUP BY r.rule_id
ORDER BY r.AD_Org_ID;
```

Are these MEP discipline registration hooks, or actual code requirement rules?
Do any reference NFPA, UBBL, spacing, pipe sizing, clearance?

### Q2: What ad_val_rule rows exist for MEP disciplines?

```sql
SELECT rule_type, rule_subtype, AD_Org_ID, COUNT(*) cnt
FROM ad_val_rule
WHERE AD_Org_ID >= 3   -- MEP: FP=3, ELEC=4, ACMV=5, CW=6, SP=7
GROUP BY rule_type, rule_subtype, AD_Org_ID
ORDER BY AD_Org_ID, rule_type;
```

If 0 rows for AD_Org_ID >= 3: MEP has no DV rules in metadata. Gap confirmed.
