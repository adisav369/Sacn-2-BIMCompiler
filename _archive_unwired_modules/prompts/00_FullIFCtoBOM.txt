## Concept

YAML is **Order input only** — it exists for the BIM Designer (generative buildings,
user opt-in). For Rosetta Stone EXTRACTED buildings, the IFC file is the sole spatial
source. The extraction pipeline reads IFC → writes `*_BOM.db`. No YAML is parsed
at extraction runtime.

ERP.db is **not affected** by extraction. It holds master products, categories,
validation rules — seeded by migrations and component_library.db. Assumed clean.

component_library.db is the **geometry + product reference**. Assumed faultless.

6. **CA (28% Unknown)** — R2 target. 726 elements on Unknown. Storey Z-bands overlap

7. **TE, WA, WL, WT** — 0 PATRN lines. These buildings may bypass discover() or
   use a different code path. Investigate.

8. **BR, RD, RL, IP (Infra)** — 0 PATRN lines, 0 storeys. The extraction is
   supposed to be abstract: "storey" is a building concept. Infra has spatial
   containers too (IfcRoadPart, IfcRailwayPart, IfcFacilityPart, IfcBridgePart).
   The pipeline assumes storeys because the code says "storey" where it should
   say "spatial container". discover() and PATTERN logging must fire for ALL
   spatial container types, not just IfcBuildingStorey. This is the root
   abstraction gap — P135 (infra walker) and 00b (YAML hardening) both trace
   back to this. Fix: rename storey → spatialContainer throughout the extraction
   pipeline, then infra gets PATTERN forensics for free.

### CRITICAL: GEO coverage gap (PATTERN is the honest signal)

GEO SUMMARY only compares elements whose `elementRef` matches IFC GUID format
(22-char base64). Buildings with non-standard GUIDs get near-zero GEO coverage:

```
PFX  | Total el | GEO el | GEO coverage | PATTERN Unknown% | GEO trustworthy?
-----|----------|--------|-------------|------------------|------------------
MO   |    3,114 |      8 |        0.3% |              84% | NO
JE   |      626 |     41 |        6.5% |              65% | NO
RA   |      442 |     96 |       21.7% |              45% | LOW
RS   |    4,133 |     90 |        2.2% |             100% | NO
RM   |    6,787 |    178 |        2.6% |              31% | NO
SH   |       58 |     58 |      100.0% |              45% | YES
IN   |      699 |    699 |      100.0% |               0% | YES
TE   |   48,428 | 48,428 |      100.0% |               —  | YES
```

**Root cause:** MO extraction GUIDs are product names (e.g., `COMPACT_MD_1._SAL_150`),
not IFC base64 GUIDs. GEO's IFC_GUID regex rejects them. "Zero drift" on 8/3114
elements is statistically meaningless.

**Lesson:** PATTERN Unknown% is the reliable extraction quality signal. GEO drift
is only trustworthy when GEO coverage ≥ 90%. For buildings with low coverage,
PATTERN is the sole forensic channel.

**Action:** GEO should use element_ref matching (exact string), not IFC GUID regex.
Any element_ref that exists in both compiled output and extraction DB should be
compared. This is a fix for `PlacementCollectorVisitor.emitGeoSummary()`.
