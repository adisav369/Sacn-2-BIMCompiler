BIM Benchmark — measured, on this machine, re-runnable

Our browser viewer (THREE.js R184, SQL-streamed geometry) vs Bonsai (Blender + IfcOpenShell) on the same 122,667-element LTU building. Two dimensions below are measured live; three are characterized from source code and honestly marked as not-yet-timed. Where we lose or tie, we say so. Every measured number was produced by a script in the repo — anyone can re-run it.

How to read this. A green MEASURED badge = a real timing produced by a witness script on this machine (cited in each card). A yellow CHARACTERIZED badge = we read both codebases and describe the architectural cost honestly, but have not run a fair head-to-head timing yet, so we show no number. Bonsai numbers are from its source and its own large-model warnings — not benchmarks we ran inside Blender. The fair comparison for a 122k model is Bonsai's recommended viewing mode (LoadLinkedProject: merged chunks + SQLite property cache + raycast pick), which is architecturally close to our viewer — not Bonsai's default one-object-per-element import, which it refuses to auto-load above 30k elements.

Two honest findings, both measured. (1) bbox-only over-reports by ~50% — 675 of the 4,000 box-overlaps are not real intersections; narrowphase removes them. (2) 1,321 near-misses (e.g. a pipe 29.4mm from a beam) that bbox-only could never find — that's clearance mode. Each verdict carries a world contact point + measurement. (4,000 = raw box-overlap pairs, no discipline/ignore filtering.)
Oursbbox R-tree from SQL (instant) → fetch geometry for candidates only → three-mesh-bvh intersection + closestPointToGeometry for clearance/contact. Intersection 0.14ms/pair, +clearance 1.5ms/pair. In-browser.
BonsaiIfcClash: tessellates every element first, per-element triangle BVH + OBB, then Möller tri-tri + ray-protrusion. Multithreaded C++. Reports exact penetration depth + protrusion/pierce classification; no published large-model timing.
VERDICT RICHNESS: PARITYIntersection + clearance gap + contact point — matched, measured.
THEY LEADExact penetration depth + protrusion/pierce — we report a bbox-overlap proxy (labelled), exact depth is lazy-reveal-on-tap (planned).
WE LEADNo up-front tessellation — broadphase is SQL over pre-stored boxes, geometry fetched only for candidates. Same verdict, less work, browser tab, zero install.

Honest correction. A "2-second pick" was feared — measurement shows median 30ms, not 2s. There is a worst-case tail (~670ms) on rays through dense geometry — R184's BatchedMesh.raycast is unaccelerated. A bbox-prefilter (reusing the clash R-tree) would tighten that tail; the median is already fine.
OursTHREE.Raycaster over BatchedMesh; post-pick is a single indexed SQL row + highlight. Median 30ms.
BonsaiBlender-native select; the click itself is cheap (cache-invalidate), IFC panel data loads lazily for visible panels only. At 122k objects the cost is Blender's depsgraph/outliner, which is why it ships the chunked viewing mode.

Save / persistence
Cost of persisting an edit
CHARACTERIZED
OursAppend one signed op to the log (O(change)) → OPFS/IndexedDB. Near-instant, but the store is proprietary.
BonsaiWrites a full standard .ifc (ISO-10303 SPF) every save: O(model) serialize + sort + Blender↔IFC sync. Slower per save, but portable, human-readable, tool-agnostic.
BONSAI WINSPortability. To export a portable IFC from our store, we'd pay the same O(model) pass Bonsai pays every save. Our win is only on incremental in-app edits.
Methodology. Measured numbers were produced on this machine by witness scripts in the repo: scripts/measure_pick.js (W-PICK-MEASURE) and scripts/measure_clash_rich.js (W-CLASH-NARROWPHASE), both driving the real viewer on LTU_AHouse (122,667 elements) headless via Playwright. The narrowphase replicates the viewer's exact element transform and uses three-mesh-bvh intersectsGeometry (true tri-tri) + closestPointToGeometry (clearance gap + contact point). Bonsai characterization is from reading IfcOpenShell/src/bonsai + ifcclash source — not benchmarks run inside Blender (running IfcClash on LTU for a real head-to-head time is the next step).

What we claim: a real two-phase clash with verdict parity to IfcClash (intersection + clearance gap + contact point, all measured), reached without up-front tessellation; pick median 30ms. What we don't claim: exact penetration depth (we show a labelled bbox proxy; lazy-reveal-on-tap is planned), nor that we beat Bonsai on render/navigation/save without a fair same-hardware timing — and Bonsai's portable standard .ifc output is genuinely better. Run the scripts yourself; correct us if a number is wrong.
